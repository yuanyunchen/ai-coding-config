日常解释与讨论用 answer-me-with-html；系统导览用 explainer；定制页面与正式审批应用用 frontend-pipeline。

## A 新装技能补上快速排版与反馈

answer-me-with-html 已装到当前 Codex，版本 0.6.1。
模型写 Markdown 草稿，附带 CLI 生成离线 HTML。
流程图、时序图、表格、主题由程序排版。
无需为每次回答重新写 CSS 或 SVG 坐标。

| 能力 | answer-me-with-html | 现有 explainer | 现有 frontend-pipeline |
|---|---|---|---|
| 核心用途 | 快速解释与讨论 | 系统导览、工作汇报 | 定制网页、应用、演示 |
| 制作方式 | Markdown → 内置渲染器 | HTML 模板与 SVG 组件 | 按产物路由到设计与开发流程 |
| 页面自由度 | 受内置组件和布局约束 | 可改说明页模板 | 可设计完整界面与交互 |
| 阅读反馈 | 面板批注、选项、复制回复 | 模板未规定批注回传流程 | 可以开发反馈表单与流程 |
| 质量流程 | 草稿语法与写作检查 | 默认阅读自查，可升档 | 默认带浏览器验证 |
| 适合输出 | 问答页、方案比较页 | 项目导览、汇报与交接 | 正式门户、品牌页面、审批应用 |

这次未开启“每次回答都附页面”的 always-on 规则。
上游普通触发范围已经较广，与 explainer 的系统解释场景有重叠。
以下选型是使用建议，尚未改写全局路由。

## B 系统架构报告：先区分总览与深入探索

给技术负责人读的系统架构报告，优先用 explainer 的 codebase 骨架。
它要求从真实代码提取主流程、模块边界与改动入口。
需要快速解释某条调用链时，answer-me-with-html 更轻便。

| 读者需要回答 | 页面内容 | 建议工具 |
|---|---|---|
| 系统解决什么问题 | 业务背景、目标、边界 | explainer |
| 请求如何完成 | 一条主流程、异常分支 | explainer 或 answer-me-with-html |
| 服务为何这样拆 | 模块职责、依赖、方案取舍 | explainer |
| 复杂节点关系怎样探索 | 可点选节点、关系与详情 | frontend-pipeline 的 starmap 分支 |
| 需要可长期维护的系统门户 | 多页面导航、搜索、更新入口 | frontend-pipeline |

示例提问：“根据代码做架构说明页，解释请求如何完成，标出外部依赖与故障边界。”
仅画出依赖图不能证明架构正确；来源、运行约束和未知项仍要核实。

## C 互动解释：用页面集中收集你的问题

answer-me-with-html 内置面板批注与 ask 选项。
你可以标记不理解的段落，写问题或选择方案。
点击页面的 Reply，将汇总文本复制回对话。
我据此解释，或只更新相关面板。

```flow LR
阅读页面 -> 批注或选择: 标明疑问
批注或选择 -> 复制回复: 汇总意见
复制回复 -> 回到对话: 粘贴给 agent
回到对话 -> 更新页面: 修正解释
```

这是一种复制回传的交互，不是页面内实时聊天。
只有存在真实待决策事项时才加入 ask，避免把解释页变成问卷。
需要页面直接保存回答、多人共同编辑时，要开发并接入相应服务。

示例提问：“把这个方案讲给我听，按背景、机制和取舍分块；把确实需要我决定的点做成选项。”

## D 外部审批：页面要围绕批准事项组织

让外部审批人先知道要批准什么，再解释为什么需要批准。
answer-me-with-html 适合审批前讨论与意见收集。
正式对外的审批说明，可由 explainer 的 report 骨架整理，再按需要定制版式。

| 顺序 | 必须讲清楚 | 判断标准 |
|---|---|---|
| 请求 | 批准事项、范围、责任人 | 看完知道自己要决定什么 |
| 背景 | 当前问题、影响、证据 | 不依赖参加过内部讨论 |
| 方案 | 推荐方案、备选方案、维持现状 | 能比较取舍 |
| 代价 | 资源、费用、时间、依赖 | 假设与确定值分开 |
| 风险 | 触发条件、缓解、回滚 | 知道失败时怎么办 |
| 结论 | 可批准、附条件批准或退回的条件 | 审批范围明确且可核验 |
| 附录 | 详细架构、数据与来源 | 需要时查得到 |

不要用内部命令、文件名或系统简称替代业务背景。
页面提供清晰的审批材料；真正的审批记录需要指定保存位置。

## E 收集意见与正式审批的实现不同

| 目标 | 可以怎么做 | 边界 |
|---|---|---|
| 我先读懂，再与你讨论 | answer-me-with-html 批注与复制回复 | 不会自动回传到聊天 |
| 外部人员审阅后给意见 | 分享可打开的 HTML，收回批注文本 | 本机文件链接不能供外部直接访问 |
| 漂亮且可打印的审批说明 | explainer 或 frontend-pipeline | 静态页面不负责身份和审批留痕 |
| 有身份、有记录的正式批准 | 审批平台，或开发带后端的审批应用 | 需要身份、版本、时间、权限与审计记录 |

如果目标明确是飞书审批，再进入飞书相关工具与流程。
HTML 上选“同意”并复制回来，可表达意见，不等于建立了完整审批系统。

## F 你可以直接这样安排

- 系统架构：“用 explainer 做给外部工程团队看的架构报告，首屏讲业务目标和系统边界。”
- 互动解释：“用 answer-me-with-html 解释这个设计，让我逐块批注，并比较备选方案。”
- 审批材料：“先整理批准事项、背景证据、成本和风险，再做外部审批说明页。”
- 正式审批：“把审批说明接入指定审批平台，保存审批身份、版本和结果。”
