# 忙时短答的上下文实验

**结论**　当前长会话处理短问时，要等输入进入回合记录，也要等第一段公开答案形成。两段都实际发生了等待，各次占比不同。长上下文是可优化因素，但不能把全部等待都归因于 token 数量。

## 上轮真实输入与输出时间线

以下以 Slack 发问时间为零点，桌面数据来自绑定回合的已记录条目。条目时间包含客户端记录行为，不等于服务端的纯计算时间。

| 问题 | 用户输入已记录 | 公开回答条目开始 | 公开回答条目完成 | Slack 回帖回执 |
|---|---:|---:|---:|---:|
| 中文短问 | 21.14 秒 | 28.59 秒 | 31.62 秒 | 31.80 秒 |
| 英文追问 | 4.84 秒 | 21.51 秒 | 23.87 秒 | 24.18 秒 |

相邻的短答推理请求分别报告 692,146 和 693,307 个输入 token，缓存命中分别为 691,328 和 692,480。该计量是模型请求的输入规模，不是 Slack 消息长度。

## 仅作用于临时副本的实验

在同一台 Mac 的真实 Codex 服务上，使用 gpt-6.2-astra、高推理设置和固定的一词问题。样本均为空闲独立回合。它们不能直接预测忙时 Slack 的端到端耗时。

- 首次试验在同一个临时副本上先问两次、压缩、再问两次。压缩前 34.095 和 4.241 秒，约 73.1 万输入 token；压缩耗时 8.021 秒，压缩后 2.364 和 1.249 秒，约 5.0 万输入 token。四次答案均与预期一致。
- 复核试验使用两个临时副本，分别保留长上下文和压缩后上下文。每组一次预热，交替顺序各发三次正式请求。长上下文两次完成（3.898 和 6.775 秒），一次在 100 秒观察窗内没有得到完成确认；短上下文三次全部完成（1.129、1.310、1.404 秒）。这组样本支持继续关注上下文成本，样本量不足以报告 p95。
- 线上按所有者选择保留原会话上下文。提交 `5e0ac28` 精简重复的插话指令，并分别记录接受插话至用户输入记录、输入记录至公开条目开始、公开条目自身耗时。权限、来源校验与原帖回执继续执行。
