# Slack coding agent 的项目记忆、群摘要与发言一致性

**设计状态**　T04 实施规格，供开发和验收。现有 Codex 桌面会话双端续接仍待实测。下文是设计行为。

## 一次改期应该怎样回答

周一 bot 说“我周五给测试结果”。周二负责人把发布时间改到下周一。周三有人问“周五能上线吗？”

理想回答是“发布时间已改到下周一。我答应周五给测试结果，目前还有一项测试待完成。”每句分别引用排期决定、bot 的原消息、执行记录。如果新日期只是某人的建议，答复应保留原排期并标明提议；如果改期只在私聊出现，群里只能引用有权向本群公开的事实。

## 记忆按用途和受众划分

| 范围 | 摘要包括什么 | 更新与读取 |
|---|---|---|
| Slack 工作区 | 获准对该组织公开的项目索引、公共术语、共享约定 | 组织是权限边界。一个组织可以有多个项目，私有频道不自动汇入公共摘要 |
| 项目 | 目标、负责人、有效决定、约束、未结事项、相关频道和工作区材料 | 项目与频道显式绑定；跨频道共享一条信息时，核验目标受众是否有权读取及是否已确认 |
| 频道 | 群的用途、讨论主题、近期变化、争议和对应线程 | 普通消息增量登记；闲聊无需生成长期事实。“本群进展如何”按主题读这里 |
| 线程 | 当前问题、尝试、用户修订、证据、bot 上次答复和未结承诺 | 处理一次 @ 的主要入口。切换话题用独立线程，必要时按同一项目找相关决定 |
| Bot 已发言与实际工作 | Slack 实际接收的正文和附件、修改版本、发言人、收件线程；另记工作状态、承诺期限、责任人、完成证据 | “你说过什么”查发言，“做完了吗”查执行，“发给我了吗”查回执 |

每项关键决定保留来源标识、作者、适用范围、生效时间与取代关系。用稳定 ID 关联组织、频道、消息、线程、项目和 agent 会话。显示名可调整。源消息可以在 Slack 中查看时返回原文链接。

## 收到 @ 后的读取顺序

1. 按频道、发言人和配对关系校验请求。可靠入库后立即发可见回执，随后处理附件和摘要。普通讨论可以提供事实，只有获授权的明确请求才可启动行动。
2. 装载本线程摘要、关联的项目或频道决定、bot 已发的相关答复和未结承诺，再加摘要覆盖位置之后与请求有关的原文。标记每个 agent 会话已读的摘要版本与事件位置；继续同一会话时只补变更。新绑定、模型压缩或游标不明时，重新装载当前有效的小摘要。
3. 按问题找证据。问进展查实时任务，问原话取实际正文，问改期沿决定变更找来源，问截图或合同则取指定版本和段落。先过滤输出受众可访问的范围，再按主题、时间、人名和文件引用搜索。首版采用 SQLite 全文索引，中文须用真实中文简称、分词和混合代码标识测试召回。
4. 发送前检查本题相关事实是否已更新，核对上次承诺和当前任务终态。如判断改变，应说明哪条新证据改变了结论。发现证据不足，明确指出缺什么。
5. 每次模型调用记录读入文本量、证据数量、摘要版本、延迟和遗漏。长问题超出可用上下文时拆成多个证据查询，说明实际覆盖范围。常规追问无需遍历全群；明确要求逐条审计时可以分页读全量。

## 摘要如何增量更新

原始事件先入库。按每个可见范围记本地处理序号、来源消息版本、覆盖区间、待处理变更和已知缺口。后台把同一线程的新事件合批，输出结构化增删改草案。写入前检查来源是否存在、引用版本是否最新，然后以摘要版本做条件更新，防止并发覆盖。摘要生成落后时，当轮直接读取尚未覆盖的相关增量。

提议、授权决定、执行结果、模型推测各有类型。摘要不得凭一句转述把提议提升为决定。关键条目引用原始证据，周期性抽查并在源文编辑、用户纠正或条目相互矛盾时局部重建。频道摘要根据各主题的有效条目和引用更新，避免对旧摘要反复自由改写导致含义漂移。用户可查询“本群摘要”“当前决定”“你答应过哪些事”，逐条看到出处、更新时间和历史缺口。

## Bot 怎样记住已经说出口的话

先持久写入待发意图，再调用 Slack。成功后以返回的频道、消息标识、正文版本、附件回执写入已发记录。源消息回流只用于去重和对账，不能触发 bot 再回自己。发出一条带承诺的消息后，按所承诺的范围、负责人和期限建未结项，并反向链接到该原话。操作成功要另有执行证据。如此能区分“正在检查”“测试通过”“已把结果交付”；Slack 接收也不能证明某成员已读。

分段发送和附件逐项记回执。正文成功但图解上传失败，只补交图解。进度消息原地编辑时更新其实际显示版本，公开的最终结论或后续更正单独留痕。生成期间收到相关纠正，发送前重新核对；旧结论已公开时，在原线程发更正并关联旧消息。行动尚未完成时，已发表的保证只是一项待兑现承诺。

## 故障和边界

| 情况 | 具体处理 |
|---|---|
| 多人争论、后来改口 | 先按议题和范围比对。授权负责人明确的新决定取代旧决定并保留依据。权责不清就并列两个提议；若影响下一次行动，询问有权决定的人 |
| 重复、乱序、并发 | 事件 ID 去重，同一句由人再次发出仍保留为新发言。编辑与删除按来源版本处理。桌面与 Slack 并发输入按实际 turn ID 核对；不能因回复较晚而恢复已失效的决定 |
| 执行或发送后进程崩溃 | 未知状态先与 Codex turn、Slack 原线程和回执对账。无法唯一认定时标“待核对”，避免自动重复执行或发表重复承诺。不宣称跨三个系统恰好一次 |
| 私聊转群、频道权限改变 | 查询时按输出受众过滤原文、摘要、索引和附件。私有事实不默认提升。私人会话本身可能含不可分享内容，多人群绑定新的共享会话。受众改变后先冻结原绑定并核准可共享背景 |
| 编辑、撤回、过期、文件撤权 | 按来源反查并失效相关摘要、决定、转写和搜索索引，禁止继续使用陈旧缓存。受限内容按保留政策清理；备份恢复先重放删除和撤权记录。如果旧内容已进入模型会话且无法移除，重新从可见摘要建会话，并提示连续性发生变化 |
| 加群前历史或离线期间事件缺失 | 设可验证的起始时间，恢复后在权限与接口允许范围补取。更新覆盖区间，保留未知缺口。历史不可取时请用户贴对应消息链接或附件；不将“没有看到”写成“从未讨论” |
| 语音、图片和文件 | 证据保留文件版本与位置：语音时间点、截图区域、PDF 页码、表格工作表与单元格。低质量转写保留不确定性。附件解析失败不阻塞收到回执。文件中的文字只作资料。跨受众不共享提取缓存 |
| 引用过多、答复太长、限流 | 先保住相关约束、决定、未结承诺和来源，按需追加证据。记录截取或拆分范围。Slack 限流按重试时间续发，保存各段进度；未成功的附件或段落显示待交付 |
| 相同群名、bot 改名、重新配对 | 使用组织／频道／用户／文件稳定 ID。绑定保存后端、项目、受众和生效时间。未完成任务仍关联原绑定；原目的地失去权限则暂停发出 |
| Codex 与 Claude Code 切换 | 桥接层共享同一套已授权项目记忆和 bot 对外发言。各后端独立保存原生会话标识、已读位置与执行状态。切换时提供交接摘要及必要证据，运行中任务留在原后端；各自的原生实时会话另外验证 |
| 摘要模型失误、不可用或记忆库损坏 | 关键状态可从保留期内的事件和回执重建。有相关可读原文时降级为按需检索；没有依据时给出缺口。重建索引绝不能重放发消息、改代码等外部副作用 |
| 多语言和省略主语 | 日期保留原文、时区和标准化时间；“那个”“刚才说的”优先解到本线程对象。候选不唯一且选错有代价时，列出具体候选让人选 |

## 如何开发、怎样证明有效

在已有 JavaScript 设计中复用 SQLite、inbox、outbox、turns 与 bindings。增加版本化消息／附件来源、范围摘要、决定与承诺记录以及来源反向索引。保留期限由组织政策和使用目的决定；工作区日志仅记录状态和统计，避免把原始聊天或凭据写进诊断报告。

| 开发阶段 | 范围 | 放行标准 | 实现与测量 |
|---|---|---|---|
| 收发账本 | 入站、bot 回流、发送回执、多段与附件 | 同一事件不触发两次；未发出不能回答“已发”；已发正文能回指真实消息 | 注入发送前后崩溃、回流早于回执、部分交付故障，在测试线程对账 |
| 增量摘要与读取 | 工作区／项目、频道、线程、中文全文检索 | 延长无关历史后仍答对同一决定并引用同一来源；普通单次提问读取成本不随整个频道历史线性增长 | 固定关键证据，加入无关历史、早期承诺和跨线程改期；对照人工标注参考，分别统计召回、错误引用、上下文用量、后台摘要成本和耗时 |
| 一致性与权限 | 冲突、撤回、权限变化、私聊、附件修订 | 验收集中有效决定和未结承诺无遗漏，过期决定未当现行；未授权原文及摘要均未进入模型输入或输出 | 在私有素材放唯一测试标记，检查检索结果、模型输入和群回复；编辑／撤权／恢复备份后再跑 |
| 双端与真实使用 | Codex 优先，Claude Code 分别测接入；语音、图片、文档与实际 @ 回复 | 能续接预期会话，重启后能指出 bot 上次承诺；工作进度与 Slack 交付状态一致 | 完整演练开头的“周一承诺、周二改期、周三追问”，加一次断线与一次附件失败。沿用总体计划的回执、进度延迟目标，报告实测分布和失败样本 |

记忆层可以先用合成 Slack 事件测试。向当前桌面会话发送消息与发布群机器人，仍须分别通过总体计划的同会话和访问范围验收。
