目标：在 Slack @ 机器人，像在当前窗口发消息一样继续任务。
Slack 能看到公开进度、等待状态和最终答案。

## A 推荐架构

```flow LR
Slack消息 -> JS桥接: 接收并确认
JS桥接 -> Codex会话服务: 发送到绑定会话
当前窗口 -> Codex会话服务: 共享同一会话
Codex会话服务 -> JS桥接: 公开进度和结果
JS桥接 -> Slack消息: 更新原线程
```

记忆来自同一 Codex 会话和既有工作区。
桥接保存频道、Slack 线程与 Codex 会话的对应关系。
它不另外调用一个普通聊天模型。

## B 当前进度与关键未知

| 项目 | 状态 |
|---|---|
| Slack 插件、CLI、工作区登录 | 已完成 |
| 项目语言 | JavaScript 已确认 |
| 本机 Codex 服务 | 已确认在运行 |
| 当前窗口能否共享会话与事件 | 尚未验证通过 |
| 机器人、实时进度与常驻服务 | 尚未实现 |

上次只读连接没有收到响应。
先排查连接、握手与探针本身，再判断兼容性。
不能把一次超时当成产品不支持。

## C 实施顺序与验收

| 阶段 | 做什么 | 通过条件 |
|---|---|---|
| P0 同会话验证 | 核对服务器、会话、工具与双端事件 | Slack 接入端与桌面能操作同一会话 |
| P1 Slack 接收 | 指定频道接收 @，先确认收到 | 未授权消息被拦截，重投不重复执行 |
| P2 上下文调度 | 空闲开始，忙时追加，支持排队与停止 | 重启保留绑定，并发输入不送错任务 |
| P3 实时输出 | 回传公开进度、等待状态和答案 | 最终输出完整，限流重试可恢复 |
| P4 常驻与联调 | 本机后台服务、重连、运行文档 | 真实 @ 到结果全流程通过 |

P0 不通过，就先报告差距并调整方案。
复制历史的新机器人不能替代同一会话验收。

## D 你在 Slack 的体验

- 发消息：先看到“已收到”，随后看到任务进度。
- 追加要求：正在工作时加入当前任务。
- 明确排队：等当前任务结束后再做。
- 查状态：直接读取状态，不另开模型任务。
- 停止：只中断绑定任务。
- 等待批准：提示回到 Codex 窗口处理。

首次上线只接本人和明确的测试线程。
给同事使用前，再确定共享背景和可执行范围。

## E 速度、记忆与故障处理

下列时间是建议验收目标，尚未实测。
正常在线时，确认消息的 p95 目标为 2 秒内。
收到公开进度事件后，Slack 更新的 p95 目标为 3 秒内。
最终答案时间取决于任务，不承诺秒回。

| 情况 | 处理 |
|---|---|
| 重复收到事件 | 根据事件 ID 去重 |
| 提交后断线，不知道是否受理 | 先核对任务状态，不直接重跑 |
| 两边同时输入 | 重新读取活跃任务，处理状态竞争 |
| 长答案 | 分段保留全部正文，附件按权限交付 |
| 内部推理和敏感工具输出 | 不转发到 Slack |
| Mac 休眠 | 无法即时响应，唤醒后重连 |

## F 开工所需与回滚

首先实施 P0，不需要先选 OpenAI API 模板或提供 API Key。
接入 Slack 时，再确定频道、线程和允许访问的人员。
第一版保留当前权限流程，不在 Slack 远程批准命令。

停止桥接服务即可恢复桌面单入口。
Codex 会话、工作区和历史记录继续保留。

[详细实施计划](../plan.md)包含文件职责、接口、测试场景和回滚要求。
