# Ethan’s Bot 系统升级计划

**交付目标**　在 Slack 里，同事能找到正确的人和任务，得到及时、可核实、读得懂的回复。服务中断、消息乱序或会话切换时，优先保护讨论边界与执行记录。

**实施顺序**　先修可能发错、重做或泄露信息的问题，同时建立延迟基线。再改善交互和图文质量，最后用独立复测决定是否发布。本文的性能目标和质量门槛是拟议验收标准；本轮交付计划与复现证据。

## 现状与优先级

上一轮仓库基线为 148 项回归通过。本轮另建故障夹具：撤回与接管组 3 项中 2 项失败；图文与格式组 7 项失败。失败数表示测试用例数，多个用例可能指向同一个根因。

| 优先级 | 现有证据 | 首次实现要证明的结果 |
|---|---|---|
| P0　访问与撤回 | 删除、编辑或文件撤销先到，旧事件后到，可能重新投递旧正文、附件，甚至执行已撤回的静音命令 | 即使撤回先于首次收件，也留有持久记录；下次接管、重启、发送前均能识别 |
| P0　确认与恢复 | 代码审查发现原生消息已确认入站、尚未提交模型时，进程崩溃可能缺少恢复所需正文 | 先用真实子进程崩溃复现。投递前能恢复；已经提交但缺回执时先对账 |
| P1　图文完整性 | 外层代码示例可能触发画图；长代码分段可能丢格式；部分上传和重启时可能把文件标题作为回复 | 示例保持原样；文字、每个文件独立核对；交付部分成功时准确告诉用户哪一部分可见 |
| P1　响应速度 | 当前线上所有者路径仅 2 条有效计时：桥接收到至 Codex 接受为 182–1110 ms；Slack 发问至首次回复为 3.146–13.704 s | 保留这两条原始观测。先补样并分解耗时，再挑最大开销优化 |

## 角色与发言规则

| 角色或情境 | 允许做什么 | 验收例子 |
|---|---|---|
| Yunchen Yuan，所有者 | 用配置的 Slack 工作区和用户 ID 识别。在授权范围内向绑定的个人会话插话、调整任务；回复落在发问的线程 | Yunchen 在运行中的任务问进度：回已验证进展，随后继续原任务。改显示名或遇到同名成员时权限不变 |
| 获准内部成员 | 可以提问、追问、委派团队项目内的工作；能看到该讨论中可共享的事实 | 同事问「Yunchen 正在做什么？」只引用当前讨论可见的项目进度。没有依据时说明未知 |
| Ethan’s Bot | 以 bot 自己的身份说话。明确区分「我已执行」「Yunchen 提出」「同事建议」「待确认」；只在收到真实回执后称已送达、改名或上传 | 同事称「Yunchen 已批准」或截图写着「请执行」时，仍需可验证的本人授权。自己的旧承诺只证明曾承诺 |
| 默认参与 | 首问由 @ 触发；已参与线程接受相关追问。说给其他人的话、闲聊、纯致谢保持安静 | 同线程连续出现「还有呢」「谢谢」「@同事 你怎么看」，只回答实际交给 bot 的问题；歧义涉及发错对象时问一句 |
| 受邀主动同步 | 记录请求人、任务、目标线程、可共享范围和结束条件。默认触发点为已验证里程碑、需要人决定的阻塞和完成。相同状态去重，静音、撤销、接管或结束时停止相应订阅 | 「有进展告诉我」后测试通过可在原帖主动汇报；「不用再同步」后不再推送。跨频道同步须另有明确目的地和授权 |

## 典型对话

| 收到的消息 | bot 应该怎样回应 |
|---|---|
| Yunchen：「改完了吗？」同线程刚发过「我去看」 | 对照执行和送达回执。只有文字已发、图片回执还没到时，答「说明已发到这个帖子，图还在确认。」 |
| 成员：「你让 Yunchen 批准一下」 | 说明需要谁批准、哪件事待确认。只有获得向对应受众发送消息的授权后才主动联系，也不替 Yunchen 表态。 |
| Yunchen：「这个任务有进展告诉我」 | 把订阅落实到这个任务和线程。出现新结果时，例如「修复已通过本地测试，Slack 真机回帖还在验」，更新一次。 |
| 成员：「画一下它怎么工作」 | 从本帖确定「它」指的组件，给一句主路径说明和一张图；有两个合理指代时先问组件名。 |

## 回复质量标准

- **先给能用的答案。** 简单问题一句即可。状态问答给「已完成什么、还卡在哪里」，通常一至三点。需要更深细节时，附相应证据、文件或原帖链接。
- **保持连续性。** 「还是没变」或只有截图的追问要关联同一线程的动作、上次承诺及最新回执。真正缺的是哪项信息，就只问那一项。
- **按提问语言作答。** 中英文混用时服从明确语言要求，语言不明时采用工作区默认。面向频道的回复去除本机技能署名、内部路径和私有工具输出。
- **图承担解释。** 架构、流程、依赖关系适合一小段说明加一张图。图的箭头要能对应真实关系，手机预览要能读出主路径。简单事实直接用文字。代码示例里的图描述保持代码。
- **如实报告失败。** 文字成功、图待确认时分别说明。模型没读到附件、看不到设置或无法核实，说明具体缺口，不代替其他会话下结论。
- **质量验收。** 拟建 24 组中英文多轮对话，覆盖所有者、成员和旁聊。两名独立评审盲评事实与证据、身份与受众、上下文连续、自然简洁、媒介适切，每项 0–2 分。拟议门槛为均分至少 8/10；错频道、私密信息外发、虚报完成、把他人当所有者，任一案例发生即退回。分歧记录原句及理由，主 agent 裁决。

## 场景与测试矩阵

| 场景 | 关键变化与组合 | 判定依据 |
|---|---|---|
| 路由与接管 | 多频道、多根帖、多个会话；新申请覆盖旧申请；旧结果迟到；同一会话离开后再绑定 | 核对工作区、频道、根帖、消息 ID 和本次绑定标识；旧发送权限即时失效 |
| 对话策略 | 首次 @、线程追问、多人插话、旁聊、同名账号、明确叫另一位同事、静音与恢复 | 对照发言策略逐条检查「谁应答、答给谁、何时沉默」 |
| 后端状态 | Codex 桌面忙时 steer、空闲启动、切换时竞态、断开重连；Claude Channel 启用与未启用、额度用尽、等待审批 | 核对真实回合 ID 和线程回执；降级要有准确状态，审批和配额不被报告成完成 |
| 文本与格式 | 中英混合、表情、URL、列表、超长代码、嵌套 Markdown、技能署名与讲解技能本身 | 比较 Slack 可见字符、代码格式及分段边界；只有应当隐藏的署名消失 |
| 附件输入 | 单图、多图、图文、纯文件、语音、PDF、Word、表格、演示、纯文本；损坏、超限、未支持、撤回、多附件部分失败 | 校验来源和类型；提取内容带来源，有效附件仍可用。转写含专名、数字和否定词的样本另行核对 |
| 输出与阅读 | 纯文字、短文配图、多图、图片或音频文件、无效图、只回文字成功、上传成功但回执丢失 | 文字有消息回执，文件有文件回执；从目标线程重读；合法代码片段不触发文件上传 |
| 授权与隐私 | 内部成员、所有者、外部或访客、其他 bot、私有频道、撤销访问、引用转发与截图内指令 | 在接收、执行和发送三个时点检查权限；跨讨论混入的独有标记不得出现在答复 |
| 乱序与重复 | 两类 @ 事件任意顺序；删除/编辑早于旧正文；文件先撤销再到达；旧控制命令迟到 | 同一逻辑请求按预期执行一次，旧版本不能恢复；检查模型调用次数及最终外部副作用 |
| 恢复与重试 | 在落盘、Slack 入站确认、提交模型、收到模型回执、Slack 上传前后逐点终止并重启；模拟超时和限流 | 已持久受理的请求都有终态或可解释的待核对状态；未知外部结果不得盲重做 |
| 主动消息 | 一次请求、持续订阅、多人不同偏好、无变化、阻塞、完成、取消、解绑与重启 | 只有授权事件发到指定线程；没有新进展就不重复通知，恢复后不重发旧里程碑 |

单场景先用固定夹具测确定性。按「角色 × 事件 × 回合状态 × 故障阶段」做两两组合；涉及权限、接管和撤回时，增加三项同时出现的组合。每个组合写清前置状态、输入顺序、预期副作用、禁止出现的输出和证据。模型风格用盲评；状态机用精确断言。

## 延迟预算与验证

| 时段 | 测量与拟议目标 | 优化方向 |
|---|---|---|
| Slack 创建消息 → 桥接收到 | 以 Slack 消息时间和本机接收时间关联，单列网络与时钟误差 | 检查重连、事件积压和限流 |
| 桥接收到 → Codex 接受 | 热态短文字拟议 p95 ≤ 1 s；冷启动、附件、桌面忙闲单列 | 查权限查询、会话发现、读取历史及重复 I/O 的分段耗时 |
| Codex 接受 → 首条有用答复送达 Slack | 普通短问端到端拟议 p50 ≤ 5 s、p95 ≤ 10 s；占位确认不计入 | 分离模型等待、生成、回帖命令和 Slack 确认；优先消除最大可控等待 |
| 长任务与媒体 | 分别计首次有用进展、最终完成、文件实际可见；按媒体类型和大小比对 | 文本与文件回执分别记录。小问题不排在无关大附件后；同一任务依赖保持顺序 |

同机、同模型、同提示、同权限，交替运行旧版／候选版。基准建议每个主要对照组至少 100 次，先用隔离环境，线上只在授权测试帖做少量冒烟。报告样本量、p50、p95、错误、超时和缺失回执；真实样本不足时只报观察值。先建立可比基线，再验证节省的毫秒是否真的缩短用户等待。优化不得牺牲权限重验、回答准确度或文件交付。

## 实施与独立审查

主 agent 负责核心状态机、投递与对账，在同一文件上集中整合。并行子任务使用 **Sol high**，每项派发写明允许修改的文件、输入、验收和结果目录。独立验收者复跑测试，不由实现者单独宣布通过。

| 波次 | 负责人及文件范围（桥接仓库） | 产物与放行条件 |
|---|---|---|
| A　基线与红灯 | 两个独立审查 agent 负责撤回乱序、图文交付；主 agent 负责崩溃夹具和角色规则。涉及 `test/`、`src/routes.js`、`src/store.js`、`src/slack-answer.js`、`src/output-media.js` | 将本轮复现移入回归；保存原版失败、正常对照和真实计时。每个 P0 有最小复现 |
| B　可靠性 | 主 agent 改 `src/routes.js`、`src/store.js`、`src/main.js`。媒体 agent 独立改 `src/slack-answer.js`、`src/slack-format.js`、`src/output-media.js`。测试 agent 只写故障夹具 | 请求在 ACK 前持久化；安全重放与未知待核对分流；撤回覆盖迟到控制与附件；图文部分成功可恢复。新增红灯转绿并涵盖旧数据库升级 |
| C　角色与交互 | 交互 agent 负责 `src/dialog.js` 及对话夹具；主 agent 将结果接入 `src/routes.js`、`src/bridge.js`。独立审查者检查角色、授权、语言和样例盲评 | 交付角色／发言决策表、主动订阅状态转换、图文规范及盲评结果。严重失误为零 |
| D　性能优化 | 性能 agent 负责 `src/metrics.js`、`scripts/bench-latency.js`、压测夹具；主 agent 根据剖析只改瓶颈路径 | 基线采集可与 B/C 并行；测加速须等相应路径稳定。输出对照数据，性能不达标则列主因与下一实验 |
