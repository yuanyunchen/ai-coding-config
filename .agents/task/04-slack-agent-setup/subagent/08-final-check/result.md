## 需要上层处理

1. **修正不确定发送的重试分类。** `src/bridge.js:260` 把所有 Slack `ok:false` 设回 `pending`。Slack 明确 `internal_error` 和 `fatal_error` 可能发生在部分写入成功之后。合成复现这些条件中的 `internal_error`，结果先落为 `pending`，回连把同一送达键发送第二次。该状态也无法通过现有 bot 回流补回执。只把确定拒绝的错误设为 `pending`，其他保留 `unknown` 等回流或人工核对。[Slack chat.postMessage 错误定义](https://docs.slack.dev/reference/methods/chat.postMessage/#errors)。
2. **明确离线工作恢复的范围。** catch-up 将漏掉的历史 @ 保存为被动资料。用户必须重新提及，才能执行未进入持久收件箱的请求。对已绑定线程，若桌面发起的 turn 在 Slack 断线期间结束，事件会在历史门控处丢弃，恢复只处理有 Slack 收件记录的 turn。合成复现回连后该 turn 查询 0 次、Slack 发送 0 次、无 outbox。若要承诺补发桌面输出，需要保留可对账的 turn 标识。依据为 `src/bridge.js:442,553–569` 与 `test/catchup.test.js:59–82`。
3. **首次登记前核准所有频道读者。** `src/slack.js:71–98,107–119` 检查外部共享状态、bot 成员资格和发令者，而发令者限制不约束消息读者。单频道和多频道访客可读获邀频道的历史，私有频道也允许有访客。已登记的频道需由负责人确认读者均可访问共享项目，后续成员变动也需同步处理。[Slack 访客权限](https://slack.com/help/articles/202518103-Understand-guest-roles-in-Slack-Understand-guest-roles-in-Slack)。
4. **完成线上时延与交互验收。** 当前运行库有 2 个进度样本、0 个确认时延样本，同时已有 1 条确认送达回执。确认时延仅在主动发送成功时记账，回流补到的回执没有计时。成功样本的 p95 也没有失败、缺失与重试分母。核对确认样本缺口，按计划保留 20 条实际确认样本，并记录两个获授权成员、双端、断线与 Claude 终端相关场景。本次只有本地合成基准。
