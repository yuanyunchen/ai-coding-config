# 结果 — T04.01/S08 撤回与接管

## 结论

本地夹具覆盖三项接管顺序。一项通过，两项复现缺陷。按用户最新要求保留证据并转入计划，仓库未修改。

## 需要上层处理

1. 接管期间先收到删除或编辑，再收到原消息时，旧正文仍进入新会话，已删除的 `/mute` 仍关闭后续回复。撤回处理目前要等旧消息已排队才留下取消记录，控制命令又在投递检查之前执行。实施时按 Slack 消息身份持久记录撤回，控制与投递都应检查，并保留编辑后禁止重播旧版本的现有语义。
2. 附件先被撤销、后随迟到事件到达时，原帖接管期间会把它存入队列，接管之后也会把同一附件提交给新会话的附件解析入口。撤销只清理当前队列和现有工作会话的本地记录，新会话使用独立存储。实施时应沿用频道的持久撤销记录，并校验排队、重放及接管后的实时入口。附件撤销后完全没有正文或可用附件的原请求也应停止投递。后者已写入夹具，当前测试优先在附件解析断言失败。
3. 验证使用本地真实路由、Bridge 和 SQLite Store，Slack 与 Codex 传输用本地替身。未验证生产 Slack 的事件顺序或附件服务响应，也未覆盖已进入 Codex 回合的内容能否移除。

## 验证

- 排队后删除，再在接管前后投递同一 Slack 消息，旧内容无交付，正常消息只交付一次 → 通过。
- 删除和编辑先到，旧消息后到；同时重投已经删除的 `/mute` → 失败，旧删除正文和旧编辑正文进入新会话，两条正常消息被静音。
- 撤销先于附件首次到达，另一次撤销发生在已排队后；接管后再送一次同样的附件集合 → 失败，已撤销文件仍到达附件解析入口。
- 在 Slack Bridge 仓库根目录执行 `node --test '<S08 派发目录>/handoff-revocation.test.js'`，退出码 1，合计 1 通过、2 失败。
