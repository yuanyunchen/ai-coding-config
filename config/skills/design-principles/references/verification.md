# 验证

交付前检查什么、怎么查、高要求时怎么派对抗审查。调用方决定跑哪一档;本文件只定义检查内容。出处见 `provenance.md` C 系列。

---

## 一、通用检查(按读者实际看到的样子查)

1. **5 秒测试**:看一眼能否说出层级、主流向、结论 / 最终产出。说不出来,先改结构再改细节。
2. **实际尺寸**:按读者实际显示宽度看(页面正文列、幻灯片投屏、PDF 打印、手机 390 宽),标题、节点名、关键数字仍可读;字号按显示像素算(visual-encoding §四)。
3. **渲染后自己看**:截图或导出后亲自打开图片逐项查,不以源码或文件尺寸代替视觉检查。本地清楚不代表嵌入、缩放后仍清楚。
4. **一致性**:节点数、箭头方向、实/虚线含义、日期与参数和正文一致;同一个数字在指标卡、图、正文里相同。

## 二、渲染自查四条(手绘 SVG 必查,盲画必踩前三条)

1. 文字是否溢出卡片右边界(估宽:中文 ≈ 1 个字号,拉丁 ≈ 0.55 个字号;估完仍要看图)。
2. 边标签是否压在连线上。
3. 同排卡片的顺序是否是读者期望的顺序。
4. 宽高比与字号是否过闸(diagrams §四、visual-encoding §四)。

## 三、内容检查(给团队外的人看时必查)

- 首屏念给非目标读者听,没有会被打断提问的地方;反向也成立,要用的人拿得到他要的。
- 首屏禁用清单逐类查过;首屏边界 = 页眉 + 指标区 + 默认展开的正文。
- 折叠掉的内容完整可达,首屏里指向它的引用仍成立。
- 对象的定位不依赖它在流程里的位置。
- 每个核心结论讲清了为什么;每张数据图有读图三拍;数字标了可信度级别。
- 连读三段没有同一个句式骨架。

## 四、对抗审查(高要求场景)

基本检查过后,派 **≥ 4 个子代理并行**,各盯一面,只报告不改文件;汇总 BLOCKER / MAJOR 后修进单一来源,重新构建、重新审,直到无主要问题。

**五个角度**(至少派 4 个):

| 角度 | 盯什么 |
|---|---|
| 内容 | 结论是否被证据支撑;有无过度声明、漏掉的反例;口径定义是否正确 |
| 视觉 | 配色语义一致、标签重叠、坐标轴、图例、留白、移动端 |
| 结构 | 章节顺序、目录锚点、编号连续、首屏与展开区分工 |
| 口径 | 对照 data-honesty §四 逐项核 |
| 质疑 | 扮演怀疑论同行,找最容易被攻击的论点,逼产物自证 |

**派单模板**(子代理无记忆,每份自带完整上下文):

> 你在审一份 {产物类型}。文件:`{绝对路径}`。事实源:`{事实/数据绝对路径}`。
> 读者:{一句话}。你的审查角度 = **{角度}**(只盯这一面,挑刺要狠)。
> 规范:`~/.claude/skills/design-principles/SKILL.md` 及其 references 中与你角度相关的文件。
> 用 webapp-testing(Playwright)打开产物,在桌面 1440 宽与手机 390 宽各截图核对。
> 产出 BLOCKER / MAJOR / MINOR 三级清单,每条给「位置 + 问题 + 建议改法」;不确定的也提,标低置信。不要改文件,只报告。

结构有争议时取原始数据或渲染结果做真值,不信单个子代理的解读。
