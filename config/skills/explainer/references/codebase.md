# 骨架:代码库导览

读者读完应能:说出系统分几块、一个请求/一条数据怎么穿过它、想改某个行为该去哪个文件。来源:用户的学习文档规范(doc-trio learning_doc),改写为 HTML 并改用代码锚点。

## 章节顺序

| # | 节 | 内容 | 图 |
|---|---|---|---|
| 0 | 页眉 | 一句话「这是什么」+ 2–3 句(解决什么问题、谁在用、读完能做什么)+ 原始标识(仓库、分支或 commit、语言/框架) | — |
| 1 | 全景 | 系统分几块、谁依赖谁。只用业务/职责名,**不出现文件名** | 全景关系图(模块级,藏细节) |
| 2 | 一次真实请求 | 选一个最有代表性的入口(一个 API、一条命令、一个任务),从输入走到输出,每一步标「哪个模块做了什么」 | 泳道或流程图;有逐步计算时加一张 ASCII |
| 3 | 模块 ×N | 每个核心模块一节,见下方模块模板 | 每节 1–2 张(关系 + 细节) |
| 4 | 设计决策 | 表:决策 / 为什么这样 / 代价或替代方案。只收读者改代码时会撞上的决策 | 表 |
| 5 | 改动指南 | 表:我想改…… / 去哪里 / 注意什么。覆盖最常见的 5–8 种改动 | 表 |
| 6 | 术语与收口 | 术语表(每个专名一句话);结尾收口图——比全景更全,纳入正文讲过的关键数据结构、回路与旁支 | 收口图 |
| — | 页脚 | 代码版本、读过的文件范围、未覆盖的部分 | — |

小仓库(自有源文件 < 10 个,不计 vendored / 第三方子目录)可合并 1+2、去掉 4,但保留全景图、真实请求、改动指南。低档另按 SKILL.md 篇幅上限:模块节 ≤ 4,其余并成一张「模块 / 职责 / 入口文件」表。

**不可运行的仓库**(规则包、文档库、配置仓):第 2 节「一次真实请求」改成「一次真实使用」——一条真实的改动请求、一份真实配置如何被读取、一篇文档如何被引用;拿不到真实记录时用一个具体样例并标「(推断)」。

## 模块模板(第 3 节每个模块)

1. **一句话职责**(结论先行):它负责什么、不负责什么。
2. **输入 → 输出**:什么进、什么出、中间产物是什么。
3. **图或表**:一张讲关系或流程;有逐步计算/状态变化时再加一张 ASCII(见 `ascii.md`)。每张图后一句「读图」+ 3–5 句解释;用表承载时表前一句结论即可。低档超过 2 张 SVG 后,模块内优先用表或 ASCII。
4. **一个真实例子**:真实的参数、真实的数据样例、真实的调用,不用 foo/bar。
5. **就近 Q&A**(模板 `dl.qa`):本模块最容易误解或反直觉的 1–3 个点,每问一句话答到位,不凑数。
6. **展开区**:`<details>` 里放代码位置(`文件:行`,每条一句说明它是什么)、关键函数签名、配置项。

## 分层(关键)

| 层 | 出现什么 |
|---|---|
| 顶层(全景、真实请求) | 只用职责/业务名,不出现文件名、类名、函数名 |
| 中层(模块节正文) | 关键模块名、类名作锚点,让懂行的人对上号,不展开实现 |
| 底层(展开区) | `文件:行`、函数签名、配置键、命令 |

每个术语首次出现时一句话说明它做什么。代码标识符不当正文主语(写「鉴权中间件先校验令牌」,不写「`verify_token()` 被调用」),标识符放括注或展开区。

## 取材要点

- 先读入口(main、路由表、CLI 定义)、依赖清单、目录结构,再顺着「真实请求」读经过的文件;不爬全仓。
- 记下每个结论对应的 `文件:行`;没读到的部分在页脚写明「未覆盖」,不推测。
- 设计决策的「为什么」优先来自注释、提交信息、文档;找不到就标「(推断)」。
- 页脚写版本:git 仓库写 commit 短哈希,非 git 目录写读取日期与最新文件日期。

## 反模式

- 全景图里出现文件名或函数名(层级错位)。
- 按目录树逐个讲文件(读者要的是职责与流程,不是目录清单)。
- 只讲结构不讲一次真实请求(读者看完仍不知道它怎么跑)。
- 设计决策只写「是什么」不写「为什么」。
- 把整段代码贴进正文。
