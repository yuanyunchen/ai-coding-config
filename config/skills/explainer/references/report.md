# 骨架:工作汇报

读者读完应能:知道做完了什么、卡在哪、自己要做什么决定,并且相信这些结论。来源:用户的周会整理/会议纪要规范(doc-trio)、分析报告方法(analytical-report)、技术交付金标准,以及全局规则「一次进度更新回答三件事」。

## 章节顺序

| # | 节 | 内容 | 图 |
|---|---|---|---|
| 0 | 页眉 | 标题 = 一句结论;2–3 句背景与边界;原始标识(任务名、时间范围、涉及的表/服务/分支) | — |
| 1 | 首屏三问 | **做完了什么**(一句话 + 一个数)· **卡在哪**(没有就写「无阻塞」)· **需要你决定**(一个决定 + 选项;没有就写「无」) | 模板的 `.brief` 三卡 |
| 2 | 状态全景 | 多条线时:每条线的上游 → 现状 → 要交的;指标卡放最关键的 2–4 个数 | 三列泳道全景 + 指标卡 |
| 3 | 核心发现 ×N | 每条一个 h2 **判断句**(「X 是 A 的问题,不是 B 的问题」);2–3 段:结论 → 机制/归因 → 未闭环部分;证据图配读图三拍 | 归因条 / 机制对照 / 数据图 |
| 4 | 风险、反例、未验证 | 不藏反例;未验证项写清缺什么证据 | 表 |
| 5 | 下一步 | 一段讲依赖(谁串行、谁可并行、外部约束);待办按人分组,每条带时间 | owner 时间线 + 待办列表 |
| — | 展开区 | 方法与口径、命令、SQL、日志、原始链接,按主题分组折叠 | — |
| — | 页脚 | 数据来源、时间、示意数值声明、待确认项与找谁确认 | — |

单人短汇报可去掉第 2 节的泳道图,只留指标卡;但首屏三问与第 5 节不省。

## 写法要点

- **只写被推翻或新确认的认知**:进度陈述放第 1、2 节,第 3 节只放判断。
- **数字**:每个数打可信度级别(A 原文/B 读图/C 推断/D 待确认);采样数标上界;同一个数全页一致;指标卡带方向与对比基准。
- **待办**:每条落到人和时间(今天/本周/下周),按 owner 分组,不混成一张大清单;依赖关系先用一段话讲清。
- **开放问题收在一处**:要定的口径、要找的人集中放在第 1 节「需要你决定」或页脚,不散在正文。
- **排查类汇报**:第 3 节按「现象 → 逐层排除 → 根因 → 证据」组织,证据(查询、日志、截图)放展开区并在正文指向它。
- **交付类汇报**:第 2 节换成「交付物清单」表(对象 / 状态 / 怎么用 / 链接),第 4 节写验收结果与已知限制。

## 反模式

- 首屏先讲过程(「本周先做了 A,然后 B……」),结论埋在后面。
- 标题是话题名(「数据分析」「进展」)而不是判断。
- 只报好消息,反例和未验证项不出现。
- 待办没有负责人或时间。
- 用颜色强调但不说明颜色含义;琥珀「待定」不写待谁确认。
