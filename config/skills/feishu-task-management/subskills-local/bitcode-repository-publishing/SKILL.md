# BitCode 仓库发布：经验型决策指南

本 skill 帮助 agent 根据现场状态选择路径，而不是照抄一条固定流程。BitCode 在工具和页面中通常称 Codebase；具体命令能力由全局 `bytedcli` skill 的 Codebase 指南负责，本 skill 只补足端到端判断、风险控制和实战经验。

## 场景路由

| 当前需要 | 读取 |
|---|---|
| 判断仓库应放在哪个域、该用 CLI 还是网页、该直推还是走 MR | 本文件 |
| 遇到 ByteTree/Groot、权限、保护分支、MR 合入或 CLI/UI 差异 | `references/field-notes.md` |
| 查询最新命令参数与 Codebase API 能力 | 全局 `bytedcli` skill → Codebase GUIDE；执行前以本机 `--help` 为准 |

## 先建立事实，不预设路径

开始时用只读检查回答这些问题；只查当前任务需要的项：

- 本地对象是什么：目录是否存在、是否已有 Git 历史、当前分支/工作树/remote、文件规模与大文件。
- 用户真正指定了什么：仓库名、显式 namespace、参考仓库 URL、“同一个域”、是否要求保留历史。
- 远端是什么状态：目标仓库是否已存在、默认分支是否为空、是否已有别人的提交。
- 当前身份能做什么：namespace 可见不等于可创建；参考仓库可读不等于可推；仓库角色、分支保护、ByteTree 绑定权限分别判断。
- 哪个执行面可用：优先结构化 CLI；CLI 缺能力、返回自相矛盾结果或需要页面专属表单时，再用已有登录态的浏览器。

不要为了凑齐信息而全量扫描。一个事实已经能决定下一步时就停止扩张检查。

## 决策维度

### 1. 仓库归属

- 用户给出完整 `code.byted.org/<namespace>/<repo>` 或参考仓库时，路径里的 namespace 是“同域”最强信号。
- namespace、Codebase group、部门、ByteTree 节点是不同维度，不要把一个可见值自动当成另一个绑定关系。
- 没有团队语境时才考虑个人 namespace；不要从上千个可见 namespace 中猜一个业务域。
- 参考仓库只有 Reporter 权限时，它仍可作为归属线索，但不能证明当前账号能向该域创建或推送。

### 2. 执行面

- `bytedcli codebase` 适合认证、namespace、dry-run、仓库/MR/检查状态和远端文件验真；机器可读场景用 `--json`。
- 网页适合 CLI 暂未覆盖或前后端约束不一致的创建表单。用户未指定浏览器时，自行尝试可用后端，不把工具选择题抛给用户。
- 不手写内部 API 绕过权限判断；CLI/UI 都失败时，报告具体缺口，而不是申请或修改更大的权限来“碰运气”。

### 3. 本地内容与首个提交

- 写操作前后各做一次文件清单，确保上传对象没有悄然缩小、移动或被全局 ignore 排除。
- 尊重现有 Git 历史和用户改动。已有仓库优先接 remote；普通目录才初始化仓库。
- `.DS_Store`、缓存等噪声可排除，但先确认忽略规则没有吞掉源码或样例。
- 空远端的首次推送尽量包含完整预期内容，因为默认分支可能在第一次 push 后立即受保护。
- 发现文件异常减少时立即停下；先找副本、快照或原位置，不能把不完整提交当成成功。

### 4. 发布路径

- 空远端且目标分支允许推送：可直接发布完整首提交。
- 默认分支已受保护：保留保护策略，推导入分支并走 MR。
- 远端已有内容：先 fetch/比较，再决定合并、rebase 或新分支；未经明确授权不 force-push。
- 首次误推了不完整提交：通常用后续分支 + MR 修正，比删除重建仓库或取消保护更稳妥。
- 合入豁免只能是当前仓库、当前提交的一次性选择，并且用户已授权完成该发布、当前账号有合法权限；不要把豁免写成默认动作。

## 权限与安全边界

- 不主动给自己加 ByteTree owner、扩大 group/仓库权限或修改长期保护规则。
- ByteTree 搜索命中不等于可绑定；个人员工节点也可能只是搜索结果，不是合法仓库归属。
- 创建仓库、推送、MR、review、merge 是不同权限，逐项用实际返回判断。
- 推送前检查明显的密钥、令牌、超大二进制和用户明确不希望公开的文件；发现疑点先停。
- 不删除已有仓库、分支或远端内容来简化流程，除非用户明确授权且目标已精确核实。

## 完成标准

只有以下证据同时成立才算发布完成：

1. 仓库 URL 的 namespace/repo 与用户意图一致。
2. 远端默认分支包含预期文件，不只是“push 命令返回成功”。
3. 本地 HEAD 与目标远端状态一致，或明确说明本地保留在哪个分支。
4. 若走 MR，MR 已 merged，必要检查为通过状态；仅创建 MR 不算上传完成。
5. 工作树没有由本次操作遗留的意外改动。

交付时只给仓库链接、目标分支/提交、文件或检查结果，以及仍存在的真实限制。
