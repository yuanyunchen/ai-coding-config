# Dorado Hive 生产任务上线

适用于“正式表已设计，需要创建或更新日更任务并接入生产依赖”的场景。业务 SQL 本身不由本文件设计。

## 1. 上线前合同

每张产出表先固定：

- 业务粒度、唯一键和分区键。
- 逻辑日期与源日期的对应关系。
- 窗口闭区间、TopK、阈值和确定性破平局键。
- 写入方式、同日重跑语义和失败保护。
- 业务保留期与物理 TTL 缓冲。
- 下游读取列、排序和事件语义。

版本表必须先取业务键唯一最新行，再判断资格；明细表必须先降到目标粒度再 join。不要用截断后的结果表反推精确原子事实。

## 2. 生产资源预检

分别验证用户账号和生产 PSM：

1. 源表读权限。
2. 目标表写权限。
3. 项目成员与发布权限。
4. cluster、DC、queue 可列出且能提交。
5. 上游任务、Sensor 或完成水位真实存在。

“表存在”“申请已提交”“个人调试成功”都不能替代生产 PSM 验证。跨机房还要检查源数据新鲜度和等价 schema；陈旧或空源不能标记 READY。

## 3. 草稿配置

正式任务草稿显式配置：

- SQL/代码。
- cluster、DC、queue。
- 调度频率和时间。
- 自定义参数与默认值。
- 上游依赖及 offset。
- 最大并发、失败重试、`runLatestWhilePending`。
- 任务 Owner、业务 Owner 和告警。

状态任务通常要求：

```text
max_concurrency = 1
self_dependency = previous cycle
runLatestWhilePending = false
failed date blocks later dates
```

只配置其中一项不能保证跨日状态一致。

## 4. 验证顺序

固定顺序：

```text
静态合同
→ sql-schema
→ task-draft explain
→ 单日真实 smoke
→ 负向失败测试
→ 发布 production version
→ 回读生产配置
```

Explain 必须带真实逻辑日期和全部模板参数，并确认窗口表发生分区裁剪。`sql-schema` 只证明粗粒度解析，不能证明 Spark 函数、模板、类型和 overwrite 安全。

## 5. 首个周期接力

若任务依赖自身前一周期，首个周期没有合法前驱：

1. 临时去掉自身依赖。
2. 用首个逻辑日期执行真实任务实例，不用 debug 冒充。
3. 与 bootstrap 分区做行数、唯一键、双向差集和全字段指纹复验。
4. 恢复自身前一周期依赖。
5. 回读依赖图，确认下一周期能解析所有父实例。

任务上线晚于当日调度点时，上游历史实例可能不会自动补建。首个自然周期前主动检查所有父实例，缺失时只补对应日期，不跳过上游检查。

## 6. 发布后的完成判定

不能只看单一状态字段：

- `check-online=false` 不一定表示 production 未运行。
- task shell 可为 runnable，但没有 production version。
- Explain 成功不等于正式实例成功。

完成证据至少包含：

- production version 与 deployed 状态。
- system instance 或正式回填实例成功。
- 目标分区验数通过。
- 参数、依赖、资源、并发、重试和告警回读一致。

等待上游、已创建任务壳、已提交发布都属于进行中，不写成完成。

## 7. 部署动作本身的陷阱(2026-07-31 实测 · bytedcli 0.111.0 · ROW/sg)

> 本节四条都是「工具说成功但没成功」或「改了 A 顺带毁了 B」。
> 时效:2026-07-31 · bytedcli 0.111.0 · region sg;换版本前先重验。

### 7.1 `task-draft update` 会**静默清空** conf 的多个字段

实测被清空的:`conf.authParam`(整个对象 → null)、`maxParallelism`、`runLatestWhilePending`。
**不报错、不提示**。其中 `authParam` 最致命 —— 任务的运行身份没了,
下次调度会静默落回项目 PSM,而报错要到**次日调度**才出现。

⇒ **改 SQL 或改 queue/cluster 之后,必须回读 conf 并逐字段比对**,
不能只看命令返回 `✓ Successfully updated`。

### 7.2 conf 里**含 SQL 本体** ⇒「恢复配置」会撤销「部署 SQL」

SQL 存放在 `conf.configuration.operator.parameter.code`。
若按「先 `task-draft update --sql-file` 推新 SQL,再 `task update-conf` 拿改前 conf 恢复配置」
这个直觉顺序做,**第二步会把第一步刚推的 SQL 盖回旧版**。

⇒ 要恢复的 conf 必须是「捕获的 conf **同时**套上新 SQL 与参数覆盖」后的产物。

### 7.3 `deployed=true` **不回答**「我的版本上线了没有」

它只说「该任务有某个已发布版本」。实测:`task online` 因权限被拒后,
`deployed` 仍是 `true`,而 `task diff` 显示 `version 8 → draft` 差异 1576 行。

⇒ 唯一诚实的判据是 **`bytedcli dorado task diff <id>` 显示 `No differences`**(已发布 == 草稿)。
更强的判据:**线上 SQL 的 sha256 == 磁盘文件的 sha256**,以及 SQL 内关键常量的实际取值。

⚠️ 另一形态:`online` 返回 `Request timeout after 20000ms` **而操作其实成功了**。
所以**成功与失败两个方向都不能信返回码**,一律回读内容。

### 7.4 `task online` 的前置检查用**任务的运行身份**校验权限

若任务要读的表只对个人账号授权、项目 PSM 无权限,**上线会被直接拒绝**
(报 `No valid privileges ... username=dorado.project.xxx` 并列出所有缺权限的列)。

解法是把任务身份显式设为个人:

```json
{"prodAuthType":"user","authMetas":[{"env":"prod","authType":"user"}],"useDoradoDefaultPsm":false}
```

**注意与 7.1 的联动**:`task-draft update` 会把它抹掉。
所以「先设身份、再部署」的顺序是错的 —— 身份会被静默还原,
而故障要到次日调度才暴露。正确做法是**部署流程内保证 conf 恢复时带上 authParam,并回读确认**。

### 7.5 「恢复配置」的判据必须含**绝对值**,不能只有「和改前一样」

7.1 的对策是「改完回读 conf 逐字段比对」。**但那是相对判据**,
它假设「改前的 conf 是好的」—— 这个假设在**单人串行操作**时成立,
在**别人先动过这个任务**时不成立。

实测(2026-07-31):他人用 `task-draft update --queue` 改队列时静默抹掉了 `authParam`;
随后的部署流程「捕获当前 conf → 推新 SQL → 恢复 conf」**忠实地恢复了一个已经坏掉的基线**。
相对判据(改后 == 改前)**全绿**,而任务身份已丢 —— 故障要到**次日调度**才暴露。

⇒ 关键字段必须断言**绝对期望值**,与基线无关:

| 字段 | 绝对期望 | 落回默认值的后果 |
|---|---|---|
| `conf.authParam.prodAuthType` | 该任务要求的身份(如 `user`) | 读不到只对个人授权的表,**次日调度才报错** |
| `conf.maxParallelism` | 该任务要求的并行度 | 并发写同一分区 |
| `conf.runLatestWhilePending` | 通常 `false` | 积压时跳过中间周期 |

**通则**:凡「恢复/回滚」类操作,判据里都要有一条不依赖基线的绝对断言。
基线可能已被污染 —— 而相对判据在基线坏掉时会**跟着一起坏,且全绿**。

## 8. 告警规则是独立对象(2026-07-31 实测)

任务上的 `conf.alarm.alarmRules` 常为 `null`,不代表没有告警 ——
liveness/timeout 规则是**独立对象**,入口:

```bash
bytedcli dorado task alarms     --task-id <id> --project-id <pid> -r <region>   # 列出绑定的规则名与 id
bytedcli dorado task alarm-rule get    --rule-id <rid> --project-id <pid> -r <region> -j
bytedcli dorado task alarm-rule update --rule-id <rid> ... --yes                # 不带 --yes 是干跑
```

阈值在 `timeoutAlarmItems`,常见三项:`latest_not_start` / `latest_not_end`(分钟)
与 `fixed_time_not_success`(`HH:MM`)。

⚠️ **`alarm-rule update` 是 read-modify-write,干跑输出里 `Task IDs` 为空** ——
若它清掉任务绑定,规则会**从任务上脱钩、彻底不再告警**,比不改糟得多。
⇒ 只为「补一句描述」这类装饰性收益去动它,**风险远大于收益**;
真要改先在干跑输出里确认绑定字段被保留。

**阈值推导口径**:每段容得下**本环节自身一次完整重试**,即
`起跑时刻 + 单次时长 + retryInterval + 单次时长 < 该环节的未完成阈值`,且各段严格递增。
⚠️ 增量口径与全量重算口径可能差 3 倍以上(本轮实测 16.5 分 vs 52.7 分),
**若周期内可能触发全量重算,必须为它单列一档**,否则天天误报。

## 9. 告警阈值:**先搞清它锚在什么上,再谈调多少**(2026-08-01 ROW 实测)

### 9.1 `running_timeout` **不是**「单次运行超过 N 分钟」

它是 **「首次提交后 N 分钟仍未成功」,跨越重试之间的等待**。
⇒ 只要 `N ≤ retryInterval`,**任何一次「需要重试才恢复」的情形都会触发它**,与运行快慢无关。

实测:`retryInterval = 3600s` 而 `running_timeout = 60min` ⇒ **结构性误报**。
该实例 `running_timeout` 触发于 `01:48:32` = 首次提交 `00:48:32` + **恰好 60:00**;
而逐实例回读的真实运行是 **6.5 / 6.7 / 7.6 / 6.0 / 8.7 / 5.4 / 4.9 分钟** —— 没有一次接近 60。

**代价不止是噪声:一个测错量的阈值会一路把结论带偏。** 本项目据此一度写下
「同任务同数据失败 7 小时 vs 成功 5 分钟 ⇒ 资源争用 ⇒ 上了 Guarantee 仍被饿死」,
整条推理链都建立在误读上,后来整条撤回。

**处置顺序不能颠倒**:**先把 `retryInterval` 降下来(如 3600 → 600),再抬 `running_timeout`**。
只抬阈值(例如 60 → 90)而不动重试间隔,等于给同一个结构性误报换个数字。

### 9.2 三个锚点各不相同,混用会算错余量

| 告警项 | 锚在什么上 |
|---|---|
| `latest_not_start` / `latest_not_end` | **cron 时刻** |
| `fixed_time_not_success` | **绝对 UTC 时刻** |
| `running_timeout` | **首次提交时刻** |

算余量前先确认每一项的锚点;把它们当成同一把尺子排「分层递增的阈值梯子」会排出错的梯子。

### 9.3 liveness 在**每次失败重试后重新触发**

一个卡住的实例今天产出了 **17 条投递**。**告警过密与告警缺失同样有害** ——
它正是"送到了但没人看"的成因之一。设计梯子时要把重试次数乘进去估投递量。

### 9.4 **liveness 似乎不评估回填实例**(n=1,未重复验证,但值得当风险)

一个卡在未满足父依赖上的**回填**实例,45 分钟内**零告警**;
换成 system 实例后 `latest_not_start`(cron+10)与 `latest_not_end`(cron+15)都准点触发。
⇒ **卡住的回填是监控盲区。** 回填重的链路(历史刷入、跨机房铺数)在回填期间
**不能只靠 liveness 兜底**,需另设回填专用的进度检查。

### 9.5 告警形态要按**失败模式**设计,不能复制粘贴

反例:某上游任务的失败是**合法的「源侧小时数不齐」**,会连着好几天复现。
照抄下游任务那套(`retry_failed` + liveness)的结果是:
`retry_failed` 每个坏源日响一次且**迟到 7 小时以上**(`6 × 3600` 才耗尽);
`running_timeout` 按 §9.1 是纯噪声;`latest_not_start` 在 `dependencies=[]` 时**永远绿**。
正解 = **单独一条 `fixed_time_not_success`,别的都不要** ——
一天最多响一次,且说的正是该说的那句话:「今天的产出缺了」。

更根本地:**「上游源不齐」本该由源新鲜度侧的监控承担**;
把它压到最下游任务的失败告警上,必然信噪比很差。

### 9.6 `ackCnt` **不能**当「告警是否被处理」的判据

它是**基线/SLA 作用域**的字段(唯一 ack API 在 `baseline_global/baseline/alarm/ack/record`)。
任务**没绑基线**时 `ackCnt` **恒为 0**,与有没有人看无关。
实测:全域一个月 Dorado 告警 Unregistered ≥1000、**Registered 0**;
某项目全量台账 7600 条,`ackCnt` 直方图 = `{"0": 7600}`。
**拿它当判据会产出一个假的行动项。**
⇒ 闭环指标改用**不依赖任何人点击**的量:`告警时刻 → 实例成功时刻` 的 MTTR。

## 10. 依赖与 conf 的互相污染(2026-08-01 EU 实测,GATE C 真的救了一次)

### 10.1 **凡走 `task-draft update` 就会抹 conf** —— `--add-dependency` 是唯一免检路径

> ⚠️ **本节初稿写成「只有 `--dependencies` 会抹 conf」,那是错的,已订正。**
> 2026-08-01 后续实测:**`task-draft update --sql-file` 的草稿重建同样会抹** ——
> 部署器第 3 步的 diff 直接打出 `authParam` LOST、`maxParallelism`/`runLatestWhilePending` → `None`。
> **正确表述:凡走 `task-draft update`(不论带哪个参数)都必须随后补 conf patch 并过 GATE C;
> `--add-dependency`(增量)是唯一不动 conf 的路径。**

新建一条链时,首次 `task online` 会因**依赖成环**被拒(A 依赖 B、B 又依赖 A 的 `[-1]` 这类
非线性拓扑很常见)。可行解法:**临时只留线性依赖 → online → 用 `--add-dependency` 把其余加回 → 重新 online**。

⚠️ **破环时若用 `task-draft update --dependencies`,它会连带抹掉
`authParam` / `maxParallelism` / `runLatestWhilePending`。**
实测当场发生:抹完之后 **GATE A(相对判据)全绿** —— 因为它比的是"改后 == 改前 + 覆盖",
而**改前的基线已经被自己污染了**;是 **GATE C(绝对值断言)报 3 条 FAIL 并拒绝 online**。

⇒ 这就是"相对判据在基线被污染时会跟着一起坏,绝对判据不会"的**实战证据**,
不是理论上的担心。任何部署器都应同时有这两道门。

### 10.2 建周期任务要建在**周期任务目录**下

往"临时查询"根目录建周期调度任务会报 **`4066`**。先建一个专用目录再建任务。

### 10.3 `EXPLAIN` 是比"字面量计数"强得多的移植判据

跨机房移植时,库名表名可能与源侧**一字不差** —— 但"名字相同不等于对象在目标侧存在/可解析"。
断言"某字面量出现 N 次"只能证明**文本**没改坏。
**正确判据:每条语句在目标机房真跑一遍 `EXPLAIN`,完成完整 analysis。** 零成本,且是唯一能回答
"在目标侧解析得到"的做法。

### 10.4 新平台坑:**字符串字面量里的 ASCII 分号会让整条语句解析失败**

注释里的分号无碍,**字符串字面量里的会**。由单变量对照(同一份 SQL 只差这一个字符,
一份 fail 一份 succeed)定位。⇒ 移植器与常量检查器都应把它列为断言项。


### 10.5 `task online` 会**重建 pending 实例并换掉它的 id**

实测:一次 online 之后,snapshot 的 pending 实例 `168299341`(version 2) 变成
**`168300694`**(version 3),新实例 createTime 与 task updateTime 只差 1 秒。

两个推论:
1. **依赖变更确实作用到已生成的实例上** —— 不需要等下一个周期才生效(这是改依赖时最大的未知,现已定死)。
2. **任何一次 online 之后,你之前记下的实例 id 全部作废。**
   ⇒ 「按实例 id 锚定」这条纪律要配一条时序要求:**锚必须建在最后一次 online 之后**,
   否则你会一直轮询一个已经不存在的 id,而它的症状是「查不到」——
   和「还没起跑」长得一样。

### 10.6 `GetAmLogFailed` **不是作业失败的原因**,是平台给"取日志"这件事配的重试策略名

实测踩过:据此写下「单条 adhoc 有规模上限,要切段绕过」——**错的,已撤回**。
真实根因用 `megatron app get` 的 `diagnostics` 挖到:**`GLIBC_2.27' not found`,
原生 HDFS JNI 客户端在部分 executor 节点上加载失败** —— 与 SQL、数据、队列争用全都无关。
某账号最近 40 个 app 里 5 个 FAILED,**5/5 全是这个签名,其他成因 0**。
切段之所以"有效",不是绕过了什么上限,而是**减少了落到坏节点的机会**。

⇒ 两条通用教训:
- **平台给的错误名可能描述的是它自己的某个动作(取日志/重试),不是你的作业。**
- 「换个跑法就好了」**不等于**「找到了原因」。在拿到真实堆栈之前,那只是一个奏效的规避。

**取真实堆栈的通道**(此前被记成"读不到",该记录可撤):
adhoc 回执里的 `jobId` **就是 Dorado 的 instanceId**,Megatron 的 app tags 里带着它,
`megatron app get` 的 `diagnostics` 就是完整 Java 栈。

## 11. 队列选型:**BestEffort ≠ 差,Guarantee ≠ 好**(2026-08-01 EU 实测)

### 11.1 先看池子大小,再看等级 —— 两者不可互相替代

EU 实测(`megatron queue list -r eu_ttp_no -j`):

| 队列 | `resource_level` | maxCPU | 已用率 |
|---|---|---:|---:|
| `root.ad_general_be` | **besteffort** | **416,486** | 52% |
| `root.ad_measurement` | guarantee | 10,800 | 12% |
| `root.ad_lookalike_prod` | guarantee | 8,400 | 13% |
| `root.ad_targeting_basis` | guarantee | 6,000 | 17% |
| `root.ad_tech_se` | guarantee | 3,600 | 0% |
| `root.ad_identity` | guarantee | 3,600 | 34% |
| `root.search_ads_compass` | guarantee | 1,200 | 0% |
| `root.app_ads_gaming` · `root.bigbang_batch` | guarantee | **0** | 不可用 |

**BE 池比最大的 GT 大 38 倍。** 在一个 41 万核、用了一半的池子里被抢占,
未必比在一个 1 万核的池子里被保障更慢 —— **这必须实测,不能靠等级标签推。**
佐证:该 BE 队列上 92 天回填、并发 6、**121 个作业零失败**。

⚠️ **`resource_level` 只出现在 `-j` 的 JSON 里,文本输出没有这一列。**
要判"有没有 GT"必须看 JSON,否则会得出"只有 BE"的错误结论(本项目真的栽过)。

### 11.2 正确做法是**按等级分工**,不是全搬到 GT

| 负载 | 特征 | 归属 |
|---|---|---|
| **日更** | 量小(几个任务各几分钟)、**要的是不被抢占**而非吞吐 | **GT** |
| **回填 / 全量重算** | 量大、被抢占了重跑即可、要的是吞吐 | **BE** |

小配额的 GT 通常足够扛日更;把回填也塞进 GT 反而会被它的小配额限住,还挤占别人。

### 11.3 "被授权提交"不等于"那是你的预算"

队列授权是 **user 维度不是 project 维度**,所以你的列表里可能出现**别的团队**的生产队列
(名字就是他们的业务名)。能提交 ≠ 应该占用。
⇒ 选定后要给出**「我们的占用是对方配额的百分之几」**这个数,并确保小到不影响对方;
项目自己的 GT 队列(若存在)优先,拿不到就走申请,而不是默认去用别人的。

### 11.4 跨集群不一定是障碍 —— 用同项目的既有任务来证

GT 与 BE 可能在**不同集群**上(本案 `wyodel02` vs `wyodel21`),看起来像个阻塞。
**判据不是猜,是找同项目里已经跑在目标集群上的任务**,核对它的
`cluster` / `dc` / `region` / `storageRegion` 是否与你的一致。
本案实证:项目内已有任务跑在 `wyodel02` / `dc=no1a` / `storageRegion=norway`,
与我们的任务同数据中心同存储区 ⇒ 跨集群不成立为障碍。

### 11.5 队列对比实验:**同题、同载荷、只变一个量**,并回读实际落到哪条队列

2026-08-01 实测设计,可直接复用:

- **载体选零写入的那份生产 SQL**(全文无 `INSERT`/`CREATE`)⇒ 整场对比**只读**,不污染生产表
- **同一个 `p_date`、字节相同的载荷**(58,946 字符),**只变 `--queue/--cluster`**
- 每条队列跑 **n=3**,取中位;**每次运行的队列都从 Megatron 回读**,不假设参数生效了
- 判据看**分布是否重叠**,不看单次差值

实测结果(BE 422,507 核 vs GT 10,800 vs GT 3,600):
**排队等待中位 33/32/33 秒、运行中位 372/368/374 秒 —— 分布完全重叠,
组内波动(~30 秒)大于组间差(~2–6 秒)。**

两条由此得出的、与直觉相反的事实:
1. **配额大 39 倍不带来任何加速** —— 作业在约 700 核处饱和(297 个历史 app 的平均核数上界),
   再大的池子买不到速度。**选队列前先量"你的作业到底能吃多少核"。**
2. **`disable_preemption=True` 可能在 BE 队列上也是开的** —— 别把"BE"直接读成"会被抢占",
   回读这个字段。本案 9 条队列(含 BE)抢占计数全为 0。

### 11.6 占用率有**两个不同的量**,不可互相替代

- **瞬时峰值占比** = 作业峰值核数 / 队列配额(本案 1,300 / 10,800 ≈ **12%**)
- **日均占空比** = 峰值 × 日运行时长 / 24h(本案 5 个任务串行 39.6 分/天 ⇒ ≈ **0.17%**)

谈"会不会影响队列所有方"要用**瞬时峰值**(那是真正会挤到人的时刻);
谈"我们占了多少资源"用**日均**。**把 0.17% 拿去回答"会不会挤到别人"是偷换。**

### 11.7 拿别的机房的**同一条链路**做容量标定

要判"这条队列够不够",最强的参照不是估算,而是**同一条链路在另一个机房的实际占用**。
本案:ROW 侧同样四个任务跑在一条 **2,750 核 GT 队列**上,长期占用 **1%**,
而 ROW 的单日数据量比 EU 大 ⇒ EU 侧 3,600 核以上的 GT 队列**必然够用**,不需要再推。

### 11.8 换队列后**必须实测生产任务路径**,adhoc 跑通不算

对比实验若全部走 **adhoc** 通道,那证明的是 adhoc 在该队列上能跑,
**不证明周期调度的生产任务能跑** —— 两条通道的提交路径、身份解析、资源申请都可能不同。

**低风险的直接验证**:挑一个**无上游依赖、幂等、耗时短**的生产任务,
对一个**历史业务日**发起 `rerun`(不要用待跑的当期业务日,那会占掉自然周期),
然后回读三件事:① 实例 `queue`/`clusterName` 是否为目标值;② 是否 succeed;
③ **它写的那个分区状态是否未变**(幂等确认)。
本案 2 分 21 秒完成,`runType=10` 与自然周期实例互不干扰。

### 7.6 `task-draft update` 抹 conf **与参数种类无关** —— 不带 `--sql` 也照抹

2026-08-01 实测补充:对新建任务跑
`task-draft update --schedule-time / --queue / --cluster / --retry-*`(**完全不带 `--sql`**),
同样把 `authParam` 从 `account` 抹成 `null`。

⇒ 正确表述是「**凡走 `task-draft update` 就必须补 conf patch 并过 GATE C**」,
不要写成「改 SQL 时要注意」或「改依赖时要注意」—— 那会让人以为别的参数是安全的。
`--add-dependency`(增量)是唯一免检路径。

**一个真实的连锁事故**(版本链已查证):
v12→v13 把 `authParam` 正确设成 `user` → **v13→v14 的队列迁移把它抹掉** →
v15 的部署"忠实地恢复"了这个已经坏掉的基线。
⇒ **线上长期跑着一个身份被抹掉的版本,而草稿里那份才是修复。**
这也是为什么 GATE A(相对判据)不够、必须有 GATE C(绝对值断言):
相对判据会把"恢复到坏基线"判成正确。

### 11.9 🔴 **Guarantee 保的是队列的配额,不是你的作业能拿到资源**

2026-08-02 实测,直接纠正了本文件此前隐含的理解:

一条 **guarantee** 队列(`maxCPU=2750`)被打到 **`used_cpu=2752`、占用率 100%**,
我们的一个**自然周期实例**因此「running」55 分钟却**从未拿到 Spark app**
(`trackingUrlsWithType = None`)。

占满它的 7 个 RUNNING 应用**全部来自另外 5 个用户** —— 同一条队列的其他使用者。

⇒ **`resource_level=guarantee` 的语义是「这条队列的配额不会被别的队列抢走」,
不是「队列内的某个用户能优先拿到资源」。队列内部仍然是先到先得。**

两条推论:
1. **「生产任务上 GT」仍然正确** —— 它保护的是队列级配额不被侵蚀,这是真实的保护。
   但它**不保证即时调度**,不要把 GT 当成"我的作业一定跑得起来"。
2. **判"作业为什么不动"要看 `trackingUrls` 有没有 app,再看队列占用率与占用者是谁** ——
   `statusAlias=running` 而无 app,意味着它在等资源,不是在跑。

⚠️ **一个我当场犯的归因错误,记下来当反面样本**:
看到"队列早先 1%、现在 100%,而我们刚跑了大量校验作业",我直接推了因果,
说"是我们自己造成的"。**实际占用者一个都不是我们。**
⇒ **占用率变化 + 我们有活动 ≠ 我们造成的。** 要看**占用者名单**,那是一条命令的事。
