# 生产写入与质量验收

## 1. 写前与写后分离

写前门禁：

- 参数合法。
- 输入日期、分区、小时和上游完成信号完整。
- TopK/阈值集合达到合同。
- 历史状态唯一且一致。
- Catalog 最新版本排序无冲突。

写后门禁：

- 行数、唯一键和事件类型。
- 排名范围、来源拆分和边界。
- 独立双向差集。
- 分区指纹。
- 下游 SQL 返回 schema。

写后发现问题不能替代写前阻断。

## 2. 校验必须强制求值

校验表达式不能只挂在可能为空的业务结果上。成熟日零新增时，非法参数或历史损坏仍必须失败。

目标引擎要真实验证：

1. 零新增 + 非法参数。
2. 零新增 + 输入/TopK不足。
3. 历史唯一性或排名损坏。

每组都应任务失败，并证明原目标分区行数与指纹不变。

## 3. Overwrite 安全

不要仅依赖“Spark 通常原子提交”的经验。对正式写法执行受控失败测试：

- 写前保存目标分区行数和分片指纹。
- 制造可控断言失败。
- 确认任务失败。
- 重算行数和指纹，必须完全一致。

Spark 读取并覆盖同一 Hive 分区时，先写任务专用临时路径，验数后再覆盖正式分区。

## 4. SQL 引擎兼容

- SG ByteQuery/Calcite 可能无法规划“相关 `NOT EXISTS` + 聚合右表”。先把右表收敛到唯一键，再用 `LEFT JOIN ... WHERE right_key IS NULL`；用双向差集证明等价。
- 数字正则通过不代表 BIGINT 安全，还要处理 0、符号、溢出和宽松模式转 NULL。
- 模板日期应形成可识别的分区谓词；Explain 检查实际 PartitionFilters。
- 最终写入边界显式 CAST 到目标 schema，不依赖粗粒度 schema 推断。

## 5. 状态与序列语义

- 用户覆盖：日内唯一边，跨日再次按 `user_id × product_id` 精确去重；不能累加每日用户数。
- 用户序列：保留重复和真实时间顺序；不能用覆盖边恢复。
- 截断快照只服务快速读取，不能用于精确商品覆盖。
- 同时间事件只能承诺确定性排序，不能声称恢复源未记录的现实先后。

## 6. Dense / 派生字段回灌

- 保留原事件行，不因空文本删除事件。
- 候选 UPDATE 还要比较最终派生文本；文本未变化的候选应抑制。
- 本地与线上一致性可使用固定哈希稳定样本，覆盖所有类别、空值和边界，不必全量复算。
- 下游依赖派生任务成功，不能读取刚写入但尚未回灌的中间状态。

## 7. 最终验收清单

- 正式实例成功，分区存在。
- 主键唯一，非法键为 0。
- 窗口、TopK、阈值和排序边界正确。
- 双向 `EXCEPT` 为 0。
- 同日重跑幂等。
- 受控失败不覆盖。
- 参数、版本、依赖、资源和告警回读一致。
- 下游 SQL 真实运行，列名、顺序和排序符合合同。

任一硬门禁未通过时状态为 BLOCKED；不以抽样、旧数据、空分区或任务壳替代正式完成。

## 8. 检查器本身怎么写(2026-07-31 一轮实战的代价换来的)

### 8.0 两条通用判据律 —— **跨域,不限 Dorado**

> 这两条同时管 Dorado 任务/实例、Hive 取数、以及任何「问远端某对象状态」的场景。
> 它们是本轮全部返工的共同根源:一轮内分别复发 **5 次**和 **5 类**。
> 单一 home 在此;`sql-query` 域的具体形态见其 `references/gotchas.md` 第四组。

#### 律一 · 判据必须锚定身份,且**锚点匹配不到必须是失败,不能是等待**

断言一个远端对象的状态时,判据里必须含一个把它与**同类对象**区分开的锚点 ——
实例 id、提交时刻、版本号,或结果自带的身份列。

**「最新的那个」「今天的那个」「列表第一个」都不是锚点**:同类对象会有多个,
而挑错的那次**看起来和挑对时一模一样**。

后半同样不可省:匹配不到时若「继续等」,轮询会**一直空转到撞上一个碰巧同名的旧对象为止**,
然后报成功。**降级路径本身就是缺陷,不是容错** —— 拿不到精确锚点时必须报错退出,
不得自动退回模糊匹配。

正面做法(已验证有效):**让结果自带身份列**。
查询里 `SELECT '<预期键>' AS probe_key`,判读时比对它 ——
**一行自证身份的数据比核对 id 更难骗**,并发场景下尤其。

#### 律二 · 先问「这个信号回答的是哪个问题」

退出码、`deployed`、`succeed` 这类字段各自只回答一个很窄的问题,
**而它们的名字听起来在回答你的问题**。本轮实测到的解耦:

| 信号 | 它其实在说 | 不是在说 |
|---|---|---|
| `hive modify field` 退出码 | 某次 API 调用的返回 | 数据有没有写、写全了没有 |
| `task get` 的 `deployed` | 该任务有某个已发布版本 | **你的**版本上线了 |
| 实例 `succeed` | 作业跑完没抛异常 | 产出内容是对的(**空输入同样 succeed**) |
| `... \| tail` 之后的 `$?` | **`tail` 的**退出码 | 前面那条命令的 |
| `AEOLUS_TIMEOUT` | 客户端不等了 | 服务端停了 |

⇒ **判据必须终止在交付物本身**(内容、指纹、逐字比对、独立交叉核对),
不终止在工具的自述。

---


> 本轮**新写**的检查器里,**有 3 个在变异测试中被自己抓出缺陷**。
> 结论不是「写得不够仔细」,而是:**检查器天然偏向「通过」** ——
> 它的失败路径最少被执行、最少被测试,而它一旦坏掉,
> **表现与「一切正常」完全一致**。所以下面每条都是写法约束,不是心态提醒。

### 8.1 每个新检查器**先做变异验证**,判据是「只有被伪造项失败」

伪造**被检查的对象**(不是伪造检查器),确认:
① 被伪造项**报失败**;② **同组其余项仍然通过**。
只满足①不够 —— 一炸全炸的检查器没有分辨力,等于没有定位能力。

### 8.2 判据可能**真空成立** —— 必须配阳性对照

反例:断言「新字段全为 NULL」用来证明「字段是新加的」。
但**所有字段都读不出来时该断言同样成立**,两种情况不可分辨。

⇒ 加**阳性对照**:同一行的邻近旧字段必须**非空**。
更强的形态:让对照按**恒等式**成立而不是「非零即可」——
「非零」会放过一个只是有噪声、并非真正响应伪造的对照。

### 8.3 判据**不适用**时必须判失败,不能真空通过

对「区间外、本就没有该类数据」的日期跑区间内的校验,阳性对照必然为 0。
此时检查器**必须报失败**并说明「对照没触发 ⇒ 上面那些零证明不了任何事」。

若判据写成「反例为 0 即通过」,这些日子会**全部误判为通过**,
并制造「多验了 N 天」的假象 —— **凭空多出来的信心比没有信心更危险**。

### 8.4 读不出来的那天,**正是最该看的那天**

检查器遇到「结果不可读 / 结果自报的身份不符 / 文件损坏」时,
**不得静默剔除该项**。实测过一个版本把读不出的天丢掉,
剩下 21 天全过就报 `exit 0` —— 而被丢掉的恰恰是最可疑的那天。

⇒ dropped 必须**计入失败**;`exit 3`(检查器自己没跑起来)**永远不得当成通过**。

### 8.5 闸门在「它保护的那次变更完成时」变红 —— 加**具名分档**,不放宽

钉死在「改前状态」的闸门,会在变更成功的**瞬间**恒红。
两种下场都坏:后续被堵死,或**操作者开始习惯性无视闸门** —— 后者更危险。

⇒ 改成多态:「改前」「改后」「上一代已部署版本」都是**有名字的合法态**,
且**报出当前是哪一态**;**第 N+1 种状态仍然报警**。
每加一态**必须变异验证**:伪造一个不在名单里的状态,确认仍然 BLOCKED。
—— 这是分档,不是放宽。

### 8.6 **先测再改门禁**,顺序反了等于拿假设改门禁

要把门禁的生效范围放宽/收紧(如把「从哪天起必须有该字段」前移),
**必须先实测该范围内确实满足新条件**,再改常量。

反过来做,改完第一次运行就会红,而**红因会被误读成业务问题**,
一个正确的修法被错误的表象否定。

### 8.7 分清「结构恒等式」与「真检验」

`SUM(CASE WHEN f THEN 1 ELSE 0 END) + SUM(CASE WHEN f THEN 0 ELSE 1 END) = COUNT(*)`
是**算术恒等式**,与数据无关,**验它等于没验**。

⇒ 写验收标准时逐条问:**这条判据存在能让它失败的数据吗?**
不存在 ⇒ 它不是判据,是装饰。真检验要落在**可能为假**的性质上
(如「该字段不得为 NULL」「与上游独立计算的口径交叉核对」)。

### 8.8 跨越多处的语义约定,**按概念穷举,不按语法搜索**

同一个常量可能有多种语法形态:`'20260724' AS x` 与 `trim('20260724') AS x`,
分处两条语句。按第一种写正则会**只改一处**,在同一文件内制造口径分裂。

⇒ 改这类约定时:先**穷举所有语法形态**,改完用**跨文件一致性检查器**复核,
并断言「旧值残留 = 0」。本轮正是靠这个检查器拦下了一次半截改动。

### 8.9 **仪器自己坏掉时,它不会说自己坏了** —— 它会说被测对象坏了,或者什么都不说

2026-07-31 一天内出现四种形态,全部同源:

| 形态 | 现场 | 假象 | 真相 |
|---|---|---|---|
| **判据在不同环境给相反答案** | 同一个预检判据,3.9 上 FAIL、3.8 上 PASS,**自己不声明跑在哪个解释器上** | 两个子智能体互相矛盾 | 判据缺一个前置断言 |
| **诊断探针自己抛异常** | `probe_failed: KeyError: 'frozen_globals_verdict'`,按设计「诊断不阻断运行」 | 序列里它看着是绿的 | **它已经是一个永远不产生信息的检查** |
| **采集脚本取不到数** | shell 数组没取到值 ⇒ 指标为空 ⇒ 触发「停滞」告警 | 任务停滞 | 任务正常,**脚本坏了** |
| **摘要不稳定** | 同一对象两次算出不同指纹 | 对象在变 | 摘要口径里混进了非对象的东西 |

**纪律**:

1. **诊断失败必须是一个可见的状态,不能被「诊断不阻断运行」吞掉。**
   「不阻断」是对**运行**的承诺,不是对**报告**的承诺——
   探针挂了要在结论里显示为 `ERROR`(第三态),不能显示为绿。
2. **告警触发前先自证仪器活着**:指标为空 ≠ 指标为坏值。
   空值路径与坏值路径必须分开处理,**空值触发的告警一律是仪器故障**。
3. **假阳性比漏报贵**:它把人派去修没坏的东西,并且消耗掉对告警的信任。

### 8.10 **只报成败的探针,失败时只能让你继续猜**

前置探针的价值是把一小时后的失败搬到两分钟内。但**报什么**决定了这两分钟值多少:

- 只报 `ok/failed` ⇒ 你知道了不行,不知道为什么 ⇒ **下一步仍是猜**
- 连**它看到了什么**一起报(工作目录列表、真实环境变量、分开测的各个依赖)
  ⇒ 一次运行就把未知维度消掉

实例:executor 端扩展模块导入失败,原始探针只报 `sys.path`——
那是**我们要求的**,不是**实际到货的**。补上 `os.listdir(cwd)` 与真实 `PYTHONPATH` 之后,
一次运行就定位了「平台把归档解包成了一个同名目录」这个此前无人知道的事实。

**推论**:当一个量不稳定时,**把它拆成正交的分量再各自报**。
一个数字说不清是「集合变了」还是「内容变了」;
拆成 shape(路径+大小)与 content(字节)两个摘要 + 按子树分解之后,
**一次运行就指到了唯一变动的那个子树**,进而认出 `.pyc` 的签名。

⇒ **诊断信息的设计,和判据的设计一样重要。**
判据回答「过没过」,诊断回答「下一步查哪」——**后者决定循环次数**。

### 8.11 验收标准不能拿「被验对象自己的声明」当证据

写验收标准时最容易混进来的一类假判据:**用产物自己声明的值,去证明产物是对的**。

实例(2026-07-31,已修正):某条验收写成「桶数必须等于 `data_bucket_count`」,
而 `data_bucket_count` **正是产物自己写下的那个字段**。
这条判据在任何情况下都成立,包括产物完全错误的情况——**它验的是「产物和自己一致」**。

与 §8.7 的区别:8.7 是**算术恒等式**(与数据无关),这里是**信息来源循环**
(判据的两端来自同一个不可信来源)。两者都表现为「永远通过」,但成因不同,查法也不同:

⇒ 逐条问:**这条判据的两端,是否来自两个独立来源?**
- 一端来自产物、另一端来自**参数合同 / 上游实测 / 独立重算** ⇒ 是判据
- 两端都来自产物 ⇒ 是自证,删掉或换来源

**独立性是判据的必要条件,不是加分项。**

### 8.12 §8.1 与 §8.9 会同时作用在**变异测试自己**身上(2026-08-01 实测)

变异测试是用来验检查器的,**但它本身也是一个新写的检查器** —— §8.1「新检查器先做变异验证」
和 §8.9「仪器坏了不会说自己坏了」对它同样成立。实测撞到的两个具体形态:

**形态一 · 抽取式变异测试的空体陷阱(本轮实测,当场发生)**
把闸门代码从脚本里 `sed` 抽出来单独喂伪造输入时,抽取模式没匹配上
(目标行有缩进、且尾部带 `|| die ...`),产出了一个 **0 行的空脚本**。
于是七档变异**全部"通过"** —— **空检查器对一切放行**。
症状很好认:**所有档位结果完全相同,且输出为空**。
⇒ 抽取之后**第一件事是断言抽出来的行数 > 0**(建议下限 5 行),
不达标就报"抽取逻辑坏了,不是闸门坏了"并**拒绝继续**,不要让它跑完给一片绿。

**形态二 · 用例构造共用同一个文件(ROW 侧已记录,此处补成因)**
用一个 `mk()` 在构造列表时把所有档位写进**同一个路径**,后写的覆盖先写的,
六档结果自然相同。⇒ **每档必须独立深拷贝 + 独立文件**。
这条与形态一的症状一样("所有档位结果相同"),但成因不同,排查时两个都要看。

**判据要三条同时成立,少一条就不算验过:**
1. 正确用例必须 `rc=0`(否则闸门在拒绝一切,不是在判特定项)
2. 每个变异用例必须 `rc≠0`
3. **每个变异用例的失败条数必须恰好等于 1** —— 只有被伪造的那一项失败。
   本轮就是靠这条抓出闸门一个真缺陷:把**解释文字**也 append 进失败列表,
   导致 1 个失败被打印成 3 条 FAIL,按条数判读的人会以为坏了三处。
   **失败数必须等于真实失败项数。**
另配**阴性对照**:显式豁免某项断言后,只违反该项的用例必须被放行 ——
否则无法区分"闸门在判这一项"与"闸门对什么都报错"。

**推论 · 检查器"根本不存在"也不是通过(§8.3 的延伸)**
§8.3 说的是判据**不适用**时必须判失败;更基础的一层是:检查器**缺失**时同样不是通过。
移植脚本到新环境时最容易发生 —— 老环境有 preflight,新环境还没写,
于是"文件不存在就跳过"顺手写成了默认行为,而调用方看到的是一路绿。
⇒ 正确做法:**缺失即拒绝执行**,要放行必须打一个显式开关,
并且开关触发时**逐条打印"你放弃了哪些检查"**。让"我放弃了什么"变成一个要动手写下来的动作。

### 8.13 断言**写对了**,但引擎可以**不执行它**(2026-08-01 实测,新形态)

把 `assert_true(...)` 放在 SQL 最终 `WHERE` 的**合取项**里 —— 哪怕放在第一个 —— **不保证它会被求值**。
**合取给了引擎自由:只要别的项已经判掉这一行,断言那一项可以根本不求值。**

实测:控制表推进作业的"仪器故障"档,期望作业 failed,**实得 succeed 且产出 0 行**
—— 于是**一个坏掉的仪器被报告成"上游很安静"**,与"数据确实不齐"这个合法状态**无法区分**。
"我把它放在第一个"这件事一文不值。

**修法:最终 `WHERE` 写成单一 `CASE`,不是合取。**

```sql
-- 错:断言可能不被求值
WHERE assert_true(NOT instrument_fault, 'gate manifest empty')
  AND observed_target = 24
  AND observed_next   = 6
-- 对:仪器故障与业务判据在同一棵求值树上,互斥且必达
WHERE CASE WHEN instrument_fault THEN assert_true(FALSE, 'gate manifest empty')
           ELSE (observed_target = 24 AND observed_next = 6)
      END
```

**推广**:任何"检查器自身健康"的断言,都不能与"被检查对象是否合格"的条件放在同一个合取里。
它们必须在**互斥分支**上,否则前者会被后者短路掉。

### 8.14 三态而非两态:**区分"数据不齐"与"仪器坏了"**

一个只有"通过/不通过"两态的门禁,**无法表达"我没法判断"**,于是必然把它归进其中一态 ——
归进"通过"是静默放行,归进"不通过"是假警报。正确形态是三态:

| 态 | 含义 | 作业结果 | 下游 |
|---|---|---|---|
| **ADMIT** | 数据齐,准入 | succeed,写 1 行 | 正常消费 |
| **WITHHOLD** | **数据**不齐 | **succeed,写 0 行** | 该日不增强,但不阻塞 |
| **FAULT** | **仪器**坏了(期望清单为空、门禁常量被篡改…) | **failed** ⇒ 重试 ⇒ 告警 | 人来看 |

**WITHHOLD 不做成失败**的理由:上游迟到是常态,做成失败会让一天的迟到把整条链堵死。
不静默的保证不来自"把它做成失败",而来自**两侧门禁** ——
若开关落后而上游其实健康,下游的**反向断言**(「要么开关说有,要么实际条数为 0」)会失败。
**落后的开关是红的,不是静默的。**

> 配套的读取判据:WITHHOLD 日会产出一个**存在但零行**的分区(空 parquet 仍有几百字节)。
> ⇒ **判据必须是"有没有行",不是"有没有分区"。**

### 8.12 解析二进制/操作码格式的检查器：**跳过 memo 就是自信地说谎**

**2026-08-01 实测。** 一个读 pickle 操作码、用来判断「类是按名字携带还是被重建」的检查器，
把 `STACK_GLOBAL` 之前的**最后两个字符串字面量**当作模块名与类名配对，**没有建模 pickle 的 memo**。

后果：当其中任一名字以 **`BINGET`**（从 memo 取回已出现过的字符串）到达时，
它报 **`class_carried_by_name: []`** —— 对一个**可证明往返成单一身份**的 payload，
给出「这个类被重建了」的结论。

**一个指向被测对象的假阴性，而故障在读取器里。**

⇒ **`memo` 不是优化细节，它是文法的一部分。** 任何按「字面量出现顺序」解析
带回引用的序列化格式（pickle / protobuf 的重复字段 / 任何带字典压缩的格式）的读取器，
**都会在压缩生效时静默给出相反的答案** —— 而压缩恰好在**重复出现**时生效，
也就是**真实负载**上生效、**小样本自测**上不生效。

**判据**：这类读取器必须配一条**阳性对照**——
构造一个「同一个名字出现两次」的负载，若读取器在第二次上给出与第一次不同的答案，它就是坏的。

**同族**（本文件已记的其它形状）：§8.9 仪器自坏、§8.10 只报成败的探针。
**共同点：被测对象没问题，读数有问题，而读数长得像结论。**

### 8.15 阳性对照本身可能是**恒真**的 —— 要防它退化

一个"阳性对照恒等式"若在**样本为空**时退化成 `0 = 0`,它就永远成立,
于是"对照通过"这件事**什么也没证明**。
⇒ 恒等式类对照必须**同时断言样本量 > 0**。实测中这道守卫是与恒等式一起写的,不是事后补的。

### 8.16 **同义反复的佐证**:两个字段由同一个分支写入时,它们一致是必然的

反例(实测):想用 `flag × source_type` 的完全划分佐证 flag 的正确性,
但 delta struct 里的 `source_type` 是常量 `'pixel'`,**由写 flag 的那同一个分支写入**
⇒ 两者一致**必然成立**,证明不了 flag 是对的。

⇒ 选佐证时先问:**这两个量是不是由同一段代码、同一个分支决定的?**
是,则它们的一致性是同义反复。**佐证必须来自一条独立的因果链**
(本案换成了上游源表的 `producer × enrich_type × matching_method` 三维交叉,
那是数据生产者写的,与我们的 flag 逻辑无关)。

### 8.17 幂等只比计数不够 —— 加一个**顺序无关的内容指纹**

"两次跑计数逐位相同"抓不到**行数相同但内容不同**。
⇒ 再加一个对全部行的、**与顺序无关**的聚合指纹(如对行级哈希做 XOR/SUM)。
同时:判据要写成"计数与指纹相同",**不能写成"所有列逐位相同"** ——
设计上就该变的列(`verified_at` 之类时间戳)会让后者必然失败,而失败原因与正确性无关。

### 8.18 "只被计数、从不被读"的对象最容易在移植时漏掉

实测:某门禁有 `expired_partition_count = 1` 这一项 —— 那个分区**只被计数,从不被读取**,
但它是 `assert_true` 的一个**合取项**。结果:目标日 D 实际需要 **91** 个连续分区而非 90,
按 90 天铺数会让门禁必红,而红的原因看起来与数据质量有关、其实无关。

⇒ 移植门禁时,**把每个合取项单独拎出来问"它要求了什么对象存在"**,
不要只看那些被 `SELECT` 引用的表。

### 8.13 读数不足以定案时，升级仪器 —— 不要升级猜测

**2026-08-01 实证，一个探针的四次进化，每一次都由一个「这组读数还是分不出来」的时刻逼出来。**

| 版本 | 报什么 | 能回答什么 | 逼出下一版的问题 |
|---|---|---|---|
| 1 | `sys.path` | **我们要求了什么** | 那**到货的**是什么？ |
| 2 | 两侧的 `id` / `__module__` / 字段 | **两个类不是同一个** | 哪一个是 import 来的、哪一个是重建的？ |
| 3 | + `*_is_what_its_module_holds`（该模块名下当前是否就持有这个对象） | **导入 vs 重建，分开了** | 那它到底走了哪条序列化路径？ |
| 4 | + driver 侧 payload 的操作码扫描（按引用/按值、写进去的模块名） | **这个对象实际走了哪条路** | —— 结案 |

**第 3 版那一格，正是让两个连续的机理判断都落空的地方**：
读数能证明"两个类不同"，却不能证明"为什么不同"，于是每个人都用自己偏好的机制去填补空白，
**而两次填补都是错的**。

**第 4 版在 driver 本地就能跑，不花集群时间** —— 而它解开的是一个耗掉六次集群运行的谜。

⇒ **纪律**：当一组读数支持多个互斥解释时，**下一步是加一个能把它们分开的读数，而不是挑一个解释去验证**。
判断标准很简单：**说得出「哪个读数能把 A 与 B 分开」，就去拿那个读数；说不出，就是在猜。**

**推论 · 探针是资产，不是脚手架。** 这个探针在六次运行里产出了六组一次比一次窄的读数，
最后那次同时给出了**失败与它的消失，在同一个进程里并排**——
对照仍然分裂、被修的类型不分裂。**只有后者的话，分不清「修好了」和「探针瞎了」。**
跑通之后不要删掉它，它是下一次同类问题的起点。

### 8.19 阻塞解除时,**解除它的那份证据通常也推翻了别的结论** —— 但你只会去看你在等的那一个

**这是 2026-08-01 实际付出的代价,不是假想。**

时间线:EU 侧长期卡在「我名下队列数 = 0」,基线据此写下
「**EU 只有 BestEffort,无 Guarantee 对应物**」并把它列为一条长期风险。
工单批复后我跑了 `megatron queue list`,**返回 9 条**,我确认了「我申请的那条到了」⇒ 卡点解除,继续推进。

**但那同一份返回里,另外 8 条全是 `resource_level=guarantee`。**
我没看,因为我当时问的问题是「我的工单到了吗」,不是「现在有哪些等级的队列」。
于是那条错误结论**又活了一整天**,一路影响了风险评估、方案设计和排期,
直到用户问了一句「队列用的都是 guaranteed 对吧」才被戳破。

**机制**:一个阻塞存在时,会长出一批**以它为前提**的下游结论。
阻塞解除的那一刻,那些下游结论**全部变成待复核状态** ——
而人只会拿新证据去回答「我等的那件事成了吗」,不会回头问「这份证据还推翻了什么」。

**操作准则**:任何长期阻塞解除时,**当场列出「以该阻塞为前提写下的结论」并逐条重判**,
不要只确认你在等的那一件。清单从记录该阻塞的那份文档里取 —— 它通常就写在同一节。

**两条加剧它的因素,都在本案出现**:

1. **默认视图藏起了那个决定性字段。** `megatron queue list` 的文本输出**没有 `resource_level` 列**,
   只有 `-j` 的 JSON 里才有。⇒ 看起来"我已经看过这个列表了",实际看的那一版**不含判据**。
   **凡要下"某某类型不存在"的结论,先确认你用的视图里有那个类型字段。**
2. **推翻旧文档时,把它仍然有效的处方一起丢掉了。** 那份基线除了写「队列数=0」,
   还写了正确做法:**「按等级分工:GT 队列跑日更、BE 吃回填」**。
   我改写状态时把整段当作过期内容处理,**处方随事实一起被丢**,
   于是后来又花时间重新推导了一遍同一个结论。
   ⇒ **作废一份文档时,事实与处方要分开判**:事实会过期,处方常常不会。

### 8.20 变异测试必须能区分「断言杀的」与「变异把代码写坏了」

一个变异档跑出 `FAILED`,有两种可能:**你想要的断言拦住了它**,或者**你的变异本身把 SQL 写坏了**。
两者在结果里长得一模一样。不区分,那档"通过"就证明不了任何事。

**做法(2026-08-01 实测采用)**:配一档**与 FAULT 档逐字节相同、只把
`assert_true(FALSE, …)` 改成 `assert_true(TRUE, …)` 的阴性对照**。
它必须 **SUCCESS**。若它也失败,说明失败来自别处,那几个 FAULT 档的结论全部作废。

这与 8.15 的"阳性对照防退化"是一对:
**阳性对照防"恒真",这条阴性对照防"恒假"。** 两个都要有。

### 8.21 分清「能不能追」与「会不会自动追」

把一个能力做出来,不等于它会在无人时自己发生。实测案例:

控制表让「哪些日子可以带 NT」变得可表达、可推进 —— **能不能追,解决了**。
但日更的时序是:主作业 `00:25` 跑,上游源约 `05:12` 才齐,推进作业 `06:30`。
⇒ 自然周期跑到 D 时 D 还没被准入 ⇒ **正确写出降级结果并通过**;
几小时后 D 被准入,却**没有任何东西回头重算 D**。**会不会自动追,没解决。**

**这个缺口不会报错** —— 每一步都"正确",只是合起来不闭环。

⇒ 验收一个「解锁类」改造时,除了问"它现在能做到吗",必须再问一句:
**"在无人干预的情况下,它会自己发生吗?"** 两个问题的答案经常不同。

补法二选一(是排期取舍,不是技术优劣):
① 把主作业推到上游齐全之后 —— 代价是**全部下游延迟**,且要重算所有告警阈值;
② 保留降级日更 + **一条定期追平作业** —— 代价是多一个对象。
选 ② 的判断依据:主要数据源快、次要数据源慢时,让多数去等少数是亏的。

### 8.22 「任务 FAILED」不等于「没有数据」—— 写后门禁是**第二条语句**

实测:某任务连续两天 FAILED,被记成"该表停在某天没有前进"。
真相是:**`INSERT OVERWRITE` 已经跑完、分区早就落地**(128 桶、2851 万行,
与门禁自己回读的 `written_row_count` 逐位相同),失败的是**紧随其后的写后门禁**。

⇒ **判"数据在不在"要回读分区,不要看任务状态。** 两者回答的是不同问题:
任务状态回答"这次运行有没有全部走完",分区回答"数据有没有落地"。
一个"写完了但门禁不满意"的任务,两个答案相反。

### 8.23 门禁的锚点若指向**别的日子**,一个合法缺席就能让它永久失效

实测形态:写后门禁断言 `hist7_day_count = 7 AND hist14_day_count = 14` —— 数的是**日历日**。
而窗口里有一天是**合法缺席**(源侧小时数不齐,已被入口门禁正确拒绝)。
⇒ 该日的数据本身**完全正常**,**杀它的是一个关于别的日子的锚点**。

更糟的是它**不是偶发**:那个洞会在 `D-14..D-1` 窗口里停留整整 14 天,
且上游若持续不完整还会产生新洞 ⇒ **日更结构性失效**。

**通用教训**:门禁里凡是"过去 N 天必须都有"这类锚点,都要问一句
**"缺席是不是可能合法?"** 若可能,判据必须从**日历日计数**改成
**与权威清单(如控制表准入日)的比较** —— 让"应该有几天"这件事由数据本身回答,
而不是由一个写死的数字回答。

改完必须验两头:**合法缺席日必须放行** + **真实异常必须仍被拦住**。
只验前者等于把门禁放松成摆设。

### 8.24 常驻定时器放在受保护目录下会**静默失效**,且脚本自己的报错路径够不着

实测(macOS):LaunchAgent 的 plist 指向 `~/Desktop` 下的脚本,
`launchctl list` **看得见该项**,但退出码 **126**,日志只有 `Operation not permitted` ——
TCC 保护了该目录,而**失败发生在 `/bin/bash` 打开文件那一刻**,
脚本里精心写的"响亮失败"逻辑**根本没机会执行**。

⇒ 常驻执行体(LaunchAgent/cron/systemd)的运行副本要放在**不受保护的路径**
(如 `~/Library/Application Support/`),源码留在工作区即可。
⇒ 部署后必须 `launchctl kickstart` 之类**真跑一次并回读退出码**,
"`launchctl list` 里有这一项"只证明注册成功,不证明它能跑。

### 8.25 🔴 **语句级死代码**:非末位的纯 SELECT 语句**整条不会被执行**

**2026-08-02 实测,本项目至今最严重的一个「永远绿的门禁」。**

现象:一个 quality 任务里有两条纯 SELECT(Q1 校验 + Q2 校验),**Q1 从来没有执行过** ——
**35 条合取项、55 个 CTE 一次都没编译**。它天天"通过",因为它根本没跑。

**成因**:引擎只执行**「末条非 SET 语句」**与**「有副作用的语句」**。
Q1 是两条纯 SELECT 里的第一条 ⇒ **整条被丢弃**。
(注意这与 8.13「断言在合取项里可能不被求值」**不是同一件事**,后者是语句内短路,这里是整条语句消失。)

**边界很干净、也很危险**:同一条链路里 delta/snapshot/nt_event 的非末位语句
都带 `INSERT OVERWRITE`(有副作用)⇒ 它们不受影响。
**只有纯校验型任务会中招 —— 而校验型任务恰恰是最不该静默失效的那种。**

**怎么发现(五条通道,构造性那条最硬)**:
1. 实例只提交 1 个 Spark app
2. 该 app 里**只有一次物化**(`save`),再往后的 exec id 返回 404
3. 那一次物化的执行计划里,**Q1 独有的表命中数为 0**
4. **构造性**:同一个 `assert_true(FALSE)`,**放第 1 条 → SUCCESS;放末条 → FAILED;单独放 → FAILED**
5. **算术**:Q1 单跑 704 s,而**包含 Q1 的完整文件只跑了 454 s** —— 比它的一半还快

**验证这类缺陷时必须配的一档**:在生产那个形状下,逐字节相同的变异 → 全绿;
**再在同一形状里改另一条(会执行的)语句 → 必须红**。
没有后面这档,前面的绿只说明「我看不见红」,不说明「那条是死的」。

**修法**:拆成两个任务、各一条语句(**不要保留"一个任务两条语句"的形状** ——
那正是成因)。合成一条语句也可行,但会产生极大的执行计划且一次失败打掉两个门禁。

**⚠️ 最该记住的一点**:**这个缺陷早就写在出问题那份文件自己的注释里,注释什么也没阻止。**
⇒ 判据必须落在**默认路径**上 —— 即"不通过就部署不了"的闸门,
而不是"文档里写着要注意"。为此写了 `assert_all_statements_execute.py` 并接进部署闸门序列,
**它自己也要变异验证**(修好的 → PASS;插入一条非末位纯 SELECT → 必须 FAIL;
其他任务 → 仍 PASS;检查器缺失 → 必须报错不能读作通过)。
