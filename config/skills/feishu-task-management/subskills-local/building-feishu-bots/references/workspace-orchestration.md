# 多组日报与工作区编排

## 父工作区

父工作区只保存跨组状态：

- bot 应用、profile、服务状态和测试群；
- `user_subscriptions`：bot 身份 sender open_id 到报告组、推送群和 enabled 的映射；
- `group_context`：chat_id 到默认子工作区，以及 `chat_id + sender_open_id` 到最近明确报告组/实体的轻量映射；
- inbox、服务账本、事件 job 状态和唤醒配置；
- 子工作区路由表。

不要在父工作区保存具体组的 watchlist、指标截图或日报格式。

## 每组一个子工作区

路径固定为 `.agent/report-workspaces/<kebab-slug>/`，至少包含：

```text
<slug>/
├── MEMORY.md
└── memory/
    ├── goal.md
    └── note/
        ├── experiment-watchlist.md
        ├── experiment-link-registry.md
        ├── daily-report-spec.md
        └── delivery-index.md
```

子工作区 MEMORY 记录：报告名称、领域 skill、自动任务/父级调度 ID、计划时间、运行幂等键、交付目录、关注实体、最后验收日期及上述 note 指针。每组必须拥有独立计划状态和交付目录。历史任务迁入时可保留原交付目录，用明确指针兼容，不能复制出两份真值。

## 同一任务的 heartbeat 限制

2026-08-03 使用 Codex Desktop 的 `automation_update` 实测：同一任务已存在 active heartbeat 时，创建第二个会被拒绝并要求更新现有 heartbeat。验证时只记录能力边界，具体自动任务 ID 留在对应工作区。

该能力边界只约束计划任务数量，不用于实时群交互。多组日报与事件唤醒分离：

1. 禁止用父级高频 Codex heartbeat 扫 inbox；无事件 heartbeat 会在可见对话留下无意义运行记录并造成刷屏。
2. 真实 @ 通过门禁和 reaction 后，由桥接器按事件触发一次处理运行；同一 `chat_id + sender_open_id + child_workspace` 在 15 分钟内续接同一短期 agent，过期后新建。短期会话不是长期真值，不能替代工作区。
3. 每个子工作区独立保存时区、计划时间、最近成功日期和幂等键；平台只允许一个 heartbeat 时，用它编排各组的日报计划，不轮询群事件。
4. 某组失败只更新该组日报状态，不阻塞事件处理或其他组；不同组的交付和推送幂等键不能复用。
5. 只有用户明确要求独立任务/项目时才建 standalone 自动任务；不能为了绕过 one-heartbeat 限制私建 cron。

## 上下文选择

运行时只提供候选上下文，不做业务意图裁决：群默认子工作区、该发送人在本群最近使用的子工作区、近期对话和消息中明确出现的对象都交给 Codex。Codex 自主判断命中范围；确实存在两个同等候选时再追问一个关键问题。不得借用另一个人的近期上下文。

控制类变更只作用于 Codex 最终确认的目标子工作区；新建独立日报组时建立新的子工作区、计划状态、交付和订阅，不复用旧组真值。

用户在群内修改日报名称、运行时间、关注对象、中间指标或订阅时，Codex 先结合当前会话确认唯一目标组，再把变化写入对应父级订阅/路由或子工作区真值，并检查现有自动任务是否仍读取旧值。用户明确说“本群订阅/取消订阅”时，当前事件的 `chat_id` 就是已授权目标，可直接写入动态订阅账本，不要求它预先存在于静态推送名单。变更回读后说明从哪一轮生效；不创建重复任务，也不只在消息里口头确认。

日报组的基本完成链路是：读取最新子工作区配置 → 生产并回读验收交付 → 按 `lark-doc-writer` 的默认规则把 Agent 新建文档设为 ByteDance 内持链接可读并回读权限 → 更新交付索引与幂等状态 → 按父工作区 enabled 订阅推送到群。每一步使用工作区当前值，避免旧会话或旧交付覆盖用户刚改的需求。用户明确要求其他分享范围时覆盖默认值。

## 会话调度与并发

1. 会话键固定为 `chat_id + sender_open_id + child_workspace`；不能仅按群或仅按发送人复用。
2. 同一键 15 分钟内续接同一 agent，15 分钟从上一次成功最终回复开始计算；首轮和每次 user ingress 先保证任务至少在当前处理窗内有效，避免长查询尚未回复就过期。失败运行不把新失败内容写成长期上下文，但重启恢复要保留上一轮已成功的 summary/turns 和原 TTL。
3. 同一键严格串行，保证“继续刚才”“把 79 也加上”不乱序；不同键使用有上限的 worker pool 并发，不能让一个慢查询阻塞所有群成员。
4. 续接时仍要重读可能变化的父/子 MEMORY、路由和目标业务文件；不要依赖会话记忆覆盖工作区的新纠正。
5. 每个事件独立防重、独立回执。服务重启可丢短期会话，但不得丢工作区记忆、pending 或幂等状态。

## 记忆与迭代

- Codex 在需要时读取命中工作区和相关 skill；连续会话不机械重读无关材料。
- 任务事实、用户纠正和长期偏好进入对应工作区；只有已经复现、验证且可跨 Bot 复用的方法才更新通用 skill。
- 记忆或复盘缺项不阻塞普通业务回复。外部变更、新文档和正式交付仍需回读后再声称完成。

## 身份与隐私

- 订阅键使用 bot 身份下的 sender open_id；user-profile open_id 只能作人工核对字段。
- 只保存 ID、显示名、任务映射和最近使用时间，不保存长期消息全文。
- 应用 Availability、应用权限、凭证和跨群操作不能由普通群消息暗中放宽；这与当前群的日报订阅不同。当前群成员明确要求订阅或取消订阅当前群时，可直接执行。不得把一个群的请求用于修改另一个未参与对话的群。

## 用户纠正的落盘

- 只有能跨 Bot 复用的名称、头像、reaction 和语言原则才经 `harness-management` 更新本 skill；单个 Bot 的名称、头像文件、语气偏好和发布状态只改父工作区。
- 订阅、群默认组和个人最近上下文改父工作区；具体业务对象、分类、维度、指标支路、报告格式和交付状态改命中的子工作区。
- 修改子工作区后检查它的独立生产任务或父级日报调度分支；修改父级交互逻辑后检查事件唤醒 prompt、job 状态机和常驻服务配置。旧提示仍会复现错误，不能只改 MEMORY。
