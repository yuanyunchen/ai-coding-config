# 技术数据链路交付图模板

适用：原始数据源、中间表、最终表、日更任务和下游读取构成的正式交付图。先查看 [`lark-doc-writer` 技术交付模板](../../lark-doc-writer/references/technical-data-pipeline-delivery.md) 登记的三张金标准 PNG。

## 三图分工

### 主链路图

回答“有哪些数据对象、分几层、主依赖是什么、下游怎么取”：

- 横向从左到右：原始数据层 → 日粒度复用层 → 最终事件层 → 下游取用。
- 同一层放在一个浅色容器中；表对象使用白底卡片，计算过程使用胶囊、虚线框或边标签，不能伪装成第七张表。
- 对象数必须与实际一致。六个表就是六个表节点；下游是消费区，不计入表对象。
- 卡片只保留：业务名、正式标识、粒度 / 核心形态、一句作用。算法细节移到分图。
- 主数据流用实线，内容比较、回灌或弱依赖用虚线；图例解释层级颜色和线型。
- 顶部用“大标题 + 一句结论型副标题”；底部可放固定边界或一句读图结论。

### 计算收益图

回答“中间表做了什么、减少了哪部分计算、还有什么没消除”：

- 每条链路一条横向泳道：原始形态 → 每日一次的预计算 → 中间表形态 → 滚动窗口复用。
- 源表和中间表卡片必须写粒度与关键字段；计算块写解析、过滤、聚合、去重等实际动作。
- 只放经过验证的数量、压缩比或工作量代理；代理估算必须在图内或图下注明“不等同于运行时降幅”。
- 同时写清剩余瓶颈，不能只展示收益。例如日内去重已固化，但 90 日跨日精确去重仍存在。

### 日更与参数图

回答“每天谁先跑、谁等待、D/E 如何对应、下游何时可读”：

- 使用三段式：信号日 D 并行 → 事件与 Dense 串行 → 下游读取。
- 任务卡写正式名称或稳定简称、输入日期、输出粒度和串并行语义。
- 显式画出 Catalog `E=D+1`、上一周期依赖、最大并发 1、失败不可越过等关键合同。
- ADD、UPDATE、REMOVE 用独立小卡说明；没有实现的事件明确标注。
- 只保留最关键参数，可用底部横条显示当前窗口、TopK、写入上限和可直接读取字段；完整范围仍放正文表格。

## 视觉合同

- 推荐画布比例 16:9 到 2:1，整体水平展开；不得做瘦高纵向长图。
- 每张图最多 3 个字号层级、3–4 个主色组；同层同色，同色同语义。
- 每个卡片正文控制在 3–4 行；完整 SQL、长条件和大段解释不得进入节点。
- 主图比正文分图更简。若主图已塞入参数、任务时序、收益数字和全部字段，说明层级失败，应拆图。
- 连线尽量水平或正交，避免穿越卡片和交叉；标签贴近对应边。
- 过程节点与数据对象必须有不同形状或底色。颜色不是装饰，而是层级编码。
- 图内使用真实对象名；禁止 A/B/C、表1/表2等代号。

## 交付前视觉检查

1. 用图片查看工具打开最终 PNG 原图。
2. 再按飞书正文约 700px 的视觉尺寸检查：标题、节点名和关键字段是否仍可读。
3. 进行 5 秒测试：能否立即辨认层级、主流向、最终表和下游。
4. 检查节点数、箭头方向、实虚线含义、D/E 日期和参数是否与 transcript 一致。
5. 检查裁切、重叠、字体过小、颜色对比不足、连线交叉和孤立节点。
6. 嵌入飞书后用浏览器复查；本地 PNG 清楚不代表文档缩放后仍清楚。

## 反模式

- 把六个对象、任务、计算动作、参数和验收数字全部堆进一张图。
- 用大段文字代替节点层级，或图后完全没有自然语言解释。
- 把计算过程画成与表对象相同的卡片，导致读者误判对象数量。
- 主图和分图重复相同细节，只是换颜色。
- 图中使用临时代号，正文才给正式名称。
- 为满足“多作图”机械增加没有新增信息的总结图。
