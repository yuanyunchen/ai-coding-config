# AI Handoff Context 写作规则(给后续 AI 接手用)

> **文档定位**:专给后续 AI(或新接手人)一次性把任务上下文吃进去的**全量、原始、可检索**文件。不追求人类可读美观,但仍要结构化。
>
> **典型场景**:跨多轮对话的长任务、需要 AI 续接、原始资料散落在 N 篇飞书 / 代码 / 群聊里、本任务核心 context 必须 verbatim 保留。
>
> **配套模版**:`templates/ai_handoff.md`(13 节骨架,内含 §13 mentor 原话 verbatim 实录块)。

---

## 一、核心原则

### 提取优先于整理
- 所有相关原始 context 都要 **verbatim 放进去**:术语、模块名、代码片段、字段、URL、参数、数值、原文 quote、mentor 口述原话。
- **不要二次概括成业务白话**来"提高可读性"。
- **宁可重复、冗余、长,也不能漏掉原始 context**。
- 整体检查必须以"**是否漏了原始素材里的相关信息**"为标准,而不是"是否够简洁"。

### 不追求人类美观,追求 AI 可检索
- 结构化、清晰、格式化(table / heading / 代码块)便于检索,但**不通过删减信息来精简**。
- 章节命名稳定可预测(§0 ~ §13),便于其他 AI 用关键词跳节。

### 双线引用
- 本地引用:`[来源:_raw_XX 第 N 行/段]` → 指向本地原始素材文件(如 `_raw_NN_*.md`),AI 可本地 grep 找。
- 远程引用:`[[标题]](url)` → 指向原始平台文档,AI 可 fetch。
- 关键 mentor 原话两种引用都要给。

---

## 二、结构骨架(13 节)

```
§0  任务快速参考(30 秒 onboarding 表)
§1  人 & 平台 & 联系方式
§2  任务定位 — 业务背景 + 任务目标 + mentor 解释 + 当前状态 + 旁证
§3  完整参数 / 配置表(JSON verbatim 粘贴)
§4  算法 / 系统链路(自顶向下三层)
§5  核心信号 / 输入 / 输出详解
§6  指标定义 & 看板路径
§7  操作流程(verbatim 步骤)
§8  已知坑 / 卡点 / 原文歧义(⚠️ 标记)
§9  决策准则速查(可直接执行)
§10 术语速查
§11 交付物清单
§12 原始资料索引(按优先级 ★ 分级)
§13 mentor / owner / 关键人物原话 verbatim 实录(分主题)  ← 关键
```

---

## 三、§13 verbatim 实录块(关键章节,不能省)

这是 AI 接手时最值钱的一节 —— 任务的"为什么"、"决策依据"、"经验阈值"都藏在 mentor 口述里。

### 写法
- 按**主题**分子节(决策依据 / 参数调优 / 重开判定 / 路径说明 / Q&A...),不按时间。
- 每条 quote 必须:
  - 用 `>` 块引用包起来
  - 保留口语化词("一般来说"、"你可以这样"、"咱们")
  - 标注 `[来源:_raw_XX 时间戳/段落]` + `[[标题]](url)`
- 不要二次润色 / 不要业务化重写。

### 示例
```markdown
### 13.1 关于参数调优的依据
> "你可以去那个打点里边搜一下这几条之路的一个 AID 的召回量大概是多少,一般来说我们把这个量乘个 0.7 来作为我们去重的一个量级,你要是设得太多的话,那全去重完了,你这条之路不就没有透出了嘛。"
> [来源:`_raw_02_meeting_transcript.md` 01:40:02][[Meeting transcript]](https://...)
```

## 四、§3 / §7 verbatim 区(JSON / 代码 / 步骤)

### §3 完整参数配置 JSON
- 整段原样粘贴,不删字段、不改键名、不省略嵌套。
- 注释行(如果原文有)也保留。

### §7 操作步骤
- 步骤来自原始 SOP / mentor 口述时,**逐字保留**。
- 不要改成"应该" / "建议",原文说"必须"就写"必须"。

---

## 五、§8 卡点 / 歧义(⚠️ 强制)

任何"原文未明确说明"、"两份资料矛盾"、"待 mentor 确认"的项,集中放这一节,标 ⚠️。

### 表格格式
| 编号 | 现象 | 原文位置 | 已尝试 | 状态 |
|---|---|---|---|---|
| ⚠️1 | {…} | {…} | {…} | 待 mentor 确认 |

后续 AI 接手时,先扫这一节就知道哪些地方不能瞎判断。

---

## 六、§12 原始资料索引(分级)

| 优先级 | 含义 |
|---|---|
| ★★★ | 必读 — 决策依据 / mentor 口述 / 平台官方 SOP |
| ★★ | 重要 — 旁证 / 类似系统案例 / 代码主链路 |
| ★ | 选读 — 背景知识 / 新人文档 |

## 七、本地文件命名约定

```
任务文件夹/
├── ai_context.md            # ← 本文件,放任务根目录(不放子文件夹里)
├── 原始素材目录/             # 原始素材
│   └── _raw_NN_*.md         # 编号原始资料
└── 输出目录/                 # 生成的交付物源
```

文件命名:`{任务名}.AI handoff.md` 或 `ai_context.md`,二选一即可,不要起花哨名字。

---

## 八、双轨持久化(强制)

> 任何为 AI 接手准备的 context handoff 文件,除了在本地保留结构化 `.md` 外,也要落到飞书生成 doc,URL 同步登记到任务输出文档清单,方便不在本机的接手者直接阅读。

操作:
1. 写好本地 `ai_context.md`。
2. 走官方 `lark-cli`(见 `feishu-task-management` 入口 + `cli.md`;旧 `mcp__feishu__*` MCP 已退役)把 markdown body 落飞书:`docx_builtin_import`(旧 MCP 记法,仅作参数语义参考,执行以 `lark-cli` 对应命令为准)把整篇 `ai_context.md` 导入成飞书文档,标题 `🤖 {任务名}.AI handoff`(用法见 `lark-doc-writer` §3)。
3. 把飞书 URL 写入任务输出文档清单。
