# 学习文档 写作规则(learning doc)

> **文档定位**:给团队新人 / 接手者读,讲清楚一个系统 / 算法 / 业务模块的**来龙去脉**:它在大盘里的位置 → 内部结构 → 本任务做什么 → 怎么调。读完应该能"对上号、知道哪儿是哪儿"。
>
> **典型场景**:算法背景说明、系统架构说明、业务模块 onboarding、技术分享底稿。
>
> **写作通则**:命名 / 格式 / 去 AI 化风格 / Callout 节制 / 可读性 / 作图选型以 `lark-doc-writer` §0 为唯一权威,本文件只写 learning 专属的结构与内容规则。
>
> **配套模版**:`templates/learning_doc.xml`(算法实验类骨架,跨业务可直接复用)。

---

## 一、结构骨架(自顶向下)

> **图的硬骨架(开局概览 + 每节双图 + 结尾细化总结,DAG/ASCII 分工见 §三):学习文档以一张开篇 DAG 全景图(鸟瞰概览、定位)起,正文每个核心逻辑用两图配合展开,以一组结尾「双收口」总结图(总结 DAG + 全链 ASCII)落。** 这是 learning 文档"帮读者最快建立逻辑骨架、再逐层展开细节"的载体,不是死格式 —— 以读者高效理解为准裁剪。
>
> **三条贯穿全文的结构标准(distill 经验,与下面骨架配合用):**
> 1. **开局 = 概览,结尾 = 展开细化总结**:开篇 DAG 只给鸟瞰骨架(有哪些模块、谁依赖谁、整条逻辑怎么走,藏细节);结尾双收口把全文细节展开到一处,且**纳入比正文更多的概念与关系**(开篇没画的横切板块、收益主线、闭环都补进来)。一头一尾呼应:进门一张地图,出门一张全展开的对账图。
> 2. **每部分逻辑用两张图配合**:正文每个核心逻辑(每个 section)用**两图配合**讲,典型 = 一张 DAG(关系 / 依赖 / 框架)+ 一张 ASCII(细节 / 公式 / 逐步),或 概览图 + 展开图。**逻辑由图承载**,不靠纯文字叙述链路。每张图紧跟一段 `**读图要点:**`(一句话点透这张图要读者抓什么),不让读者自己猜图。
> 3. **降文字比重 · 逻辑用图解 · 文字只做解释**:正文显著降低文字比重;流程 / 关系 / 公式 / 逻辑一律用图解承载;**文字只承担四件事 —— 解释图、Q&A、概念 / 术语解读、讲"为什么"**。一句话:图讲逻辑,文字讲解释。文字若在复述图里已画清的链路 = 冗余,删。

```
【开篇全景 · 一张 DAG】(mermaid → 渲 PNG → Image 块)
  └ 概念 / 框架骨架的高层鸟瞰:有哪些模块、谁依赖谁、整条逻辑怎么走。
    ⛔ 不用 ASCII 当开篇全景(高层概念关系是 DAG 的活,见 §三)。

一、整体流程
  1.1 业务/系统的多层粒度对照(表)
  1.2 开篇 DAG 全景图(mermaid TB/LR,渲 PNG)—— 承载概念/框架骨架、模块与关系的鸟瞰;
       概述层,藏底层细节(这一节就是上面的"开篇全景")
  1.3 单服务内部架构(mermaid TB,subgraph 并行子模块)—— 把 1.2 某个大 entity 展开一层
二、本任务在整体里的定位(mermaid TB,新模块与同级模块并列)
三、本模块算法 / 实现详解
  3.1 模块定位(一句话目标)
  3.2 核心输入信号(表 + 字段名 + 取数路径)
  3.3 反查 / 处理链路(细节用 ASCII <code>:公式逐步推导、同名变量换分身)
  3.4 端到端算法 N 步流程(细节用 ASCII <code>;纯拓扑/分支汇合可 mermaid)
  (每个 section 末尾就近放该节的 Q&A,挑本节最容易卡住的点)
四、调参方向 / 现象-决策对照(表)
(计费/出价类文档:必须含 出价 → 计费 → 评估 完整链路;风控/流控逻辑作为补充板块)
五、术语速查
  5.1 主线术语
  5.2 代码模块名(选读) — 真实 DAG / 节点 / 函数名

【结尾总结 · 双收口图】(范例见 `templates/learning_doc.xml` §6.1/§6.2 结尾收口图;放全文最后,作读者"一图带走")
  ① 变量依赖 DAG(mermaid → 渲 PNG → Image 块):圆角=变量、方角=公式、
     实线=算出、虚线=复用/回灌 —— 尽量含全文核心概念与关系。
  ② 全链 ASCII 公式图(<code language="text">):从输入层逐阶段串到闭环、
     节点带单位、边写公式、IF/ELSE 分支 —— 把所有细节展开到一张。
```

可裁剪:非算法类系统可以删 §三.3、§四;但 §一、§二、§五、**开篇 DAG 全景**、**结尾双收口图**必须保留。

> **结论先行骨架(distill 经验范本 · 讲清一整套系统 / 多篇成体系时优先用此章节顺序)**:上面的「整体流程 → 定位 → 详解 → 调参 → 术语」骨架适合单篇算法实验;当目标是**讲透一整套系统**(或拆成主入口 + 多板块成体系)时,按下面这条更"结论先行"的章节顺序组织,每篇都自成一篇:
>
> ```
> 标题 + 一句话引导块(这篇是什么、读完得到什么、不展开什么)
> 一句话定位       结论先行:这套东西做什么、为什么重要(一句话压到位,再展开)
> 在全链路的位置    + 本篇输入→输出:先放定位图(开篇/导航 DAG)+ 一句读图要点,
>                  再用 输入 / 输出 / 中间产物 三段讲清本篇在大盘的位置与 IO
> 正文(每个核心逻辑一节)
>   ├ 每节双图配合:DAG(关系/框架)+ ASCII(细节/公式),每图紧跟 **读图要点:**
>   ├ 文字只做:解释图 / 概念解读 / 讲"为什么"(降文字比重)
>   ├ 每对象给 输入→输出 + 一个具体例子(抽象机制后跟一个真实数据的例子)
>   └ 就近 Q&A:本节最易卡住/反直觉的点,放在节末(不单设全局 FAQ)
> 关键概念锚点      本篇术语速查:零黑话,每个首次出现的专名一句话解释或指术语表
> 全文总收口        双收口:① 总结 DAG(关系网,比正文更全、纳入更多概念)
>                  + ② 全链 ASCII(逐步完整逻辑,输入→逐阶段→输出 + 归因)
> (多篇体系)footer nav:返回总览 | 下一篇 | 术语表
> ```
>
> 这条顺序与上面的图硬骨架不冲突,是它在"成体系讲系统"场景下的落地排法:开篇 DAG 全景 = 这里的「在全链路的位置」定位图,结尾双收口 = 这里的「全文总收口」。**主入口篇额外加一节 §数字怎么读**(见 §四下「数字来源分级」),把全体系数字的 A/B/C/D 级别口径一次讲清。

> **概念讲解型变体(强制裁剪,非内部系统时)**:本骨架默认「广告内部实验」语境(§1.2 服务拓扑全景 / §1.3 单服务内部架构 / §二 本任务定位 都假定有一个内部系统可拆模块)。当主题是**讲清一个通用概念 / 机制**(from-knowledge,任务没给内部业务系统),这些「服务拆模块」节套不上,按下面裁剪:
> - **删 §1.3 单服务内部架构、§二 本任务定位** —— 概念没有"单服务内部 / 在大盘的位置",硬画会编造结构。
> - **开篇 DAG 全景仍保留并升格为主图**:§1.2 的开篇 DAG 改画**概念自身的逻辑结构鸟瞰**(定义→机制→推导→边界),代替服务拓扑;高层关系仍用 DAG,不退 ASCII。
> - **正文 ASCII 展开概念的推导细节**:§三 改为讲概念的机制与推导(为什么成立 / 一阶条件 / 退化端点),公式逐步推导用 ASCII <code>;§3.2 信号表 → 改成概念的关键量 / 假设对照表。
> - **结尾双收口仍保留**:① 变量依赖 DAG(概念间依赖)+ ② 全链 ASCII 公式图(完整推导链),作概念的最终对账。"完整链路必须作图"对概念同样成立。
> - **Context 框走 §五 的 from-knowledge 写法(R11)**:声明"本文为概念讲解、不依赖内部业务文档",列可核查的公开权威参考,不伪造内部链接。
> - 命名 / 格式 / 去 AI 化 / 深度地基等通则不变,仍以 `lark-doc-writer` §0 为准。
>
> 一句话示范:`广告竞价中的出价收缩(bid shading)` —— 删服务拓扑,§1.2 开篇 DAG 画概念骨架(胜率→盈余→一阶条件→收缩因子谁依赖谁),正文 ASCII 逐步推 `胜率曲线 W(b) → 盈余 W(b)(v−b) → 一阶条件 W'(b)(v−b)=W(b) → 收缩因子 s=b*/v`,结尾双收口(变量依赖 DAG + 全链 ASCII),Context 声明概念讲解并引 Google Ad Manager 一价说明 / EOS 2007。

> **开篇 DAG 全景 + 结尾双收口(强制,learning 的图骨架)**:
> - **开篇放一张 DAG 全景图**(§1.2,渲 PNG → Image 块):= **高层模块 / 概念全景(鸟瞰)** —— 领域 / 链路框架,有哪些模块、谁依赖谁、整条逻辑怎么走,藏底层细节。**⛔ 不用 ASCII 当开篇全景** —— 高层概念关系是 DAG 的活(§0.6 / §三)。
> - **结尾放一组总结图**(全文最后,双收口,范例见 `templates/learning_doc.xml` §6.1/§6.2 结尾收口图):① **变量依赖 DAG**(渲 PNG;= **变量依赖格 / 展开全文细节、完整概念关系** —— 圆角=变量、方角=公式、实线=算出、虚线=复用/回灌)+ ② **全链 ASCII 公式图**(`<code language="text">`,从输入逐阶段串到闭环、节点带单位、边写公式、IF/ELSE 分支)。尽量展开全文所有细节、含完整概念与关系,作读者"一图带走"的最终对账。
> - 🔴 **开篇 DAG ≠ 结尾 DAG(强制,必须是两张不同的图,不能同一张画两遍)**:开篇 = **模块 / 概念全景鸟瞰**(领域 / 链路框架,模块与关系);结尾 = **变量依赖格**(展开全文细节 / 完整变量与公式关系)。两图焦点与节点集**必须不同** —— 开篇若也只画纯变量依赖骨架,就和结尾收口图同质重复了(producer 实测易踩此坑)。概念讲解型变体下尤其注意:开篇画领域 / 链路框架,结尾才画变量依赖。
> - 📐 **开篇全景渲染尺寸**:保持文字清晰可读,别过宽 / 字太小 —— **长宽比闸(含开篇导览放宽例外)以 `dag-flow-diagram`「布局与长宽比」为唯一权威**;**2× 渲染**(渲染器默认走 graphviz `dot`,见 `dag-flow-diagram`)。
>
> **完整链路必须作图(强制)**:出价→计费→评估、nobid 完整链路这类端到端逻辑,**必须用图承载**,不能用纯文字叙述链路 —— 端到端的**逐阶段公式推导用 ASCII**(同名变量换分身讲得最清楚),纯**拓扑 / 分支汇合**可用 mermaid DAG。其他章节也多用不同模块、不同层级的图,减少文字叙述。Non-bid 部分同样遵守"开篇 DAG 全景 + 结尾双收口"。
>
> **不写独立「相关文档」节(强制)**:开头橙色 Context callout 已列出全部原始文件出处,正文**不再**单开「相关文档」章节重复罗列。源文档跳转只放在 Context callout 与正文 inline 引用里。
>
> **Q&A 按 section 放(强制)**:不再单独设一节全局「常见问题与解答」,而是把 Q&A **就近放到每个 section 末尾**,挑该节最容易卡住 / 混淆的点(概念边界、易错口径、为什么这么设计),每问一句话答到位,不凑数。用层级区分代替堆叠高亮框。
>
> **source 矛盾处理(强制)**:若 source 之间口径矛盾(如 rank_bid 等概念定义冲突),结合自身知识取**正确口径**呈现,把矛盾点写出来并标注不同 source 引用,保证无歧义、不漏写、不瞎写。

## 二、风格规则

> 措辞去 AI 化、Callout 节制、命名前缀等通则见 `lark-doc-writer` §0。本节只保留 learning 专属的「自顶向下分层」。

### 自顶向下分层(learning 专属,关键)
| 层级 | 出现的内容 |
|---|---|
| 顶层(整体流程/分层) | 只用业务概念,**不出现**模块名 / 代码 / 接口 |
| 中层(单层内部) | 出现关键模块名作为锚点(如 pSort / snake_merge),让懂行的人对上号,但不展开实现 |
| 底层(本任务自己) | 每个算法步骤旁以**斜体灰色括注** `<i>(模块名)</i>` 形式标注真实 DAG / 节点 / 函数名 |

- 每个术语首次出现时括号简注一句它干啥。
- **永远不贴**:thrift IDL 字段名、文件路径、JSON 全节点路径 —— 这些归操作文档。
- **代码模块名降级**到 §5.2 "代码模块名(选读)"章节,主叙述只讲算法做什么。

## 三、作图规则(重点)

learning 文档的图统一按 `lark-doc-writer` §0.6 作图选型分流。**分工一句话:DAG(mermaid→PNG)= 框架 / 概念关系 / 全景 / 总结;ASCII(`<code>`)= 细节 / 公式链路逐步展开。** 据此,learning 文档 = **开头 DAG 全景** → 正文 ASCII 展开细节(+ 就近 Q&A)→ **结尾总结图(DAG + ASCII 双收口)**。这里只列 learning 场景的额外约束:

- **开篇 DAG 全景(§1.2)**:用 DAG 画概念 / 框架骨架的高层鸟瞰,渲 PNG 嵌 Image;藏底层细节。**不用 ASCII 当开篇全景**。
- **正文每节双图配合(降文字 · 逻辑用图)**:正文每个核心逻辑用**两图配合**讲 —— 典型 = 一张 DAG(关系 / 依赖 / 框架)+ 一张 ASCII(细节 / 公式 / 逐步),或 概览图 + 展开图。逻辑由图承载,文字只解释图 / 讲"为什么" / 做概念解读,显著降文字比重(不用纯文字复述图里已画清的链路)。**每张图紧跟一段 `**读图要点:**`**(一句话点透要读者抓什么),不让读者自己猜图。
- **正文 ASCII 只展开细节(§3.3 / §3.4)**:公式 / 流程链路的逐步推导(同名变量在不同阶段换分身)、局部细节用 ASCII;**不画高层概念 / 框架**(那是 DAG 的活)。定宽表只用于枚举对照。
- **结尾双收口图**:① 变量依赖 DAG(mermaid→PNG)+ ② 全链 ASCII 公式图(`<code>`),尽量展开全文细节、含完整概念与关系,且**比开篇全景纳入更多概念与关系**(横切板块 / 收益主线 / 闭环都补进来),呼应"开局概览、结尾细化总结"。
- **完整链路必须作图**:出价→计费→评估、nobid 全链等端到端逻辑用图承载,不用纯文字叙述;逐阶段公式推导用 ASCII,纯拓扑/分支用 DAG。
- **拆分原则**:不同阶段拆为独立 entity(广告召回 / 商品召回服务 / 广告精排 是三个 node);流程图标题用名词短语。
- mermaid 节点三层视觉分层、edge 带数据/公式标签、核心节点高亮(见模版 §1.2 / §1.3 / §二与结尾 DAG 示例)。
- ASCII 代码块内 `<` `>` `&` 必须转义(见 `lark-doc-writer` §0.6 / §2);每行 ≤ ~72 等宽列(CJK 计 2)。

## 四、引用规则

- 事实 / 数值 / 操作步骤 / 原文 quote 句末必须 inline 引用 `[[标题]](URL)`,放在句号之前。
- 区分出处类型:mentor 逐字稿 / AI notes / 原始平台文档 / 配套自产文档,在跳转标题里要看得出来。
- **source 矛盾**:取正确口径呈现,矛盾点写出来并标注不同 source 引用,保证无歧义、不漏写、不瞎写。

### 数字来源分级(A/B/C/D,凡引数字必标级别)

正文里的数字按来源可靠级别标注,级别越高越可作硬结论;成体系时在主入口篇单设一节「数字怎么读」一次讲清口径。

| 级别 | 来源 | 标注方式 |
|---|---|---|
| **A · 原文确证** | 原始文档文本 / 表格直给 | 硬结论,一般不额外标注(默认即 A) |
| **B · 图源待复核** | 仅从内嵌图目视读出 | 标「(取自内嵌图,待图源复核)」 |
| **C · 推断** | 靠语境 / 常识推断 | 标「(推断)」,不单独作硬结论 |
| **D · 待项目确认** | 原文未给 / 需工程业务核实 | 标「(以项目实际为准)」 |

- **每对象给 输入→输出**:讲一个模块 / 算子 / 阶段时,先点清它的输入与输出(+ 必要时中间产物),让读者拿得住"什么进、什么出"。
- **抽象机制后跟一个具体例子**:讲完机制配一个带真实数据的例子(一条真实序列 / 一组真实数值),不停在空泛描述(对齐 `lark-doc-writer` §0 具体例 · 真实数字)。

## 五、开头标准结构(两个 callout,顺序固定)

样式与通则见 `lark-doc-writer` §1.4。learning 补充:
- 概述框分要点说明各板块写了什么,**另补一句整体介绍**(文档作用、主要内容),要点化、去 AI 化。
- Context 框列原始文件可跳转 link,**每个原始文件加一句简要介绍**;配套互链操作 / handoff URL。
