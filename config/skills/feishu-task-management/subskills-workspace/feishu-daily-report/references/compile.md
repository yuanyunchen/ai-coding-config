# 阶段二 · 整理日报(compile)

> **定位**:把当天的工作整合成一篇正式日报,落到飞书 Drive 的 `Daily Report` 文件夹、按周归档。
>
> **核心原则**:**多来源整合,重质量**。不要只依赖记录片段——agent 跨会话记不住自己干过什么。成文要综合三方信息:①**用户口述的当天清单 + 产出文件链接**(主线)、②**实际回读产出文件**(飞书文档走官方 `lark-cli` 拉全文,必要时顺 link 回读 context 文件补前因/口径)、③当天 md 记录片段(agent 自述,补充)。三方去重整合,冲突以原始文件为准。
>
> **内容标准**:用最简洁精炼的语言讲清楚**做了什么、东西的逻辑/原理是什么**,讲到合适的程度;**结构化但不琐碎**——用要点/表格组织、避免大段密集文字,但每条要表达完整、读着自然,相关的点合并、该用完整句子讲清的逻辑就用完整句子,不为拆而拆。充分引用 context 文件与产出文件。
>
> **篇幅红线**:成品**约 1.5 页 / 一屏半**,能很快读完。**全 vs 精**是这篇日报的核心张力——见下面「篇幅与裁剪」一节,先读它再动笔。
>
> **template 参照**:成文骨架与排版见 `templates/daily_report.xml`(一篇已验收的真实日报)——整理时优先复制它再替换内容。注意 template 是**排版骨架**(callout 样式 / 表格 / `<hr/>` 分隔 / 命名),不是篇幅标尺;它示例了 7 节,而你的日报该压到下述上限,**别照搬它的长度**。

## 〇、篇幅与裁剪(先读,贯穿全程)

> 实践教训:日报最容易犯的毛病是**太长**——七八个一级节、每节糊一段密文字、把过程流水和内部技术细节全搬进来,读者要划三四屏才看完,真正的产出反而被淹没。日报是给人快速读的工作记录,不是归档文档。**呈现要精简,但覆盖要全**——这两件事不矛盾,见文末「全 vs 精」。

### 篇幅上限(可操作启发)

成品控制在**约 1.5 页 / 一屏半**,目标是「30 秒扫完概述、2 分钟读完全文」。落地启发:

- **一级节 ≤ 5 个**:当天事项多于 5 件时,把同性质的小事合并成一节(如几个零散的基建小修合并为「基础设施补强」一节),或并入概述 bullet 一句带过,不每件都立节。
- **每节 2--5 句的体量**:一节 = 一句点题(做了什么 + 结论)+ 一两句逻辑/原理 + 按需一个小列表或表格。讲清就停,不续写背景铺垫。
- **整篇正文 ≈ 一屏半**:粗略以「概述 callout + ≤5 节 + 小结 callout」为度,正文总字数控制在约 600--900 字(中文),宁可偏短。超了就回头砍,而不是另起一节解释。**字数口径 = 流动散文(flowing prose)**:只数正文段落里成句的散文,**不含** callout 文本 / 表格单元格 / bullet 条目文字(这些是索引 / 对照,不是流动正文)。所以全量 body 字数会高于这个口径(实测全量 ~1030 而流动散文才 ~650 是正常的),**别按全量误判超标而过度删减**。
- **概述与小结各一句话密度**:概述每条 bullet 一句话;小结分维度但每维度一句话。它们是索引,不是正文复制。

### 只保留需要展示的细节(裁剪规则)

写每一条前问一句:**「读者需要看到这个细节吗?」** 不需要就砍。

| 保留(有展示价值) | 砍掉(低价值,徒增长度) |
|---|---|
| 做了什么(动作)+ 得到的结论/判断 | 怎么一步步做的过程流水(试了 A 再试 B 再回退) |
| 为什么这么做、东西的逻辑/原理(讲到够懂) | 内部实现技术细节(具体函数名、block ID、参数全集、调试经过) |
| 关键数据 / 方向 / 取舍(2--3 个并列项用表格) | 冗长枚举(把 8 个要点全列;留最关键的 3 个,其余「等」带过) |
| 一条指向产出/学习文档的 `<cite>`(细节下沉到那里) | 把学习文档/产出文档的内容搬进日报(重复、臃肿) |
| 跨节都需要的背景,只在最合适的一处讲一次 | 自指废话(「下面介绍」「这是今天唯一的 X」)、重复总结 |

裁剪不是漏写——**该说的事都要覆盖到**(见第一节三方来源),但每件事**点到结论 + 一条引用**即可,深的内容靠 `<cite>` 下沉。

### 结构 ↔ 自然文字的平衡

> **呈现目标(默认照此)= 要点化 · 结构化 · 平衡语言 · 可读**:每节默认「一句点题(自然语言)+ 短要点 bullet」组织;要点用**完整自然短句**、不写电报式碎词,也不糊成密集长段;扫读友好。下面三条是它的落地。

不要走极端:**整篇都是结构化条目/表 ≠ 好**(碎、冷、读着累),**整段密集长文字 ≠ 好**(扫不动)。要的是**简短自然句 + 适度结构**:

- **叙述用 1--2 句自然话**:点题、讲逻辑/原理用完整句子,像成熟工程师写的内部记录,自然不口语。
- **关键处才上结构**:并列对象 / 多个方向 / 数据对比 → 小列表或表格;有先后顺序 → 列表。不是每节都得有列表,讲一句话能说清的就一句话。
- **留白、文字别太密**:节与节之间 `<hr/>` 分隔;一节内别糊成一大坨——一个点题句之后,需要展开才用列表,不需要就收住。扫读友好优先于信息密度。

### 克制(callout / 表 / 图)

- **callout 只两个**:开场一个蓝色概述、结尾一个绿色小结,足够。正文不再插高亮框。
- **表 / 图按需,不堆**:有 2--3 个并列项要对比才上表;要画链路图才渲染 PNG。日报以「短自然句 + 少量列表」为主体,不为有结构而硬塞表格图示。

### 全 vs 精(把这对张力记住)

daily-report 的内核——**不偷懒、不凭印象、覆盖当天主要产出**——**完整性原则保留不变**。但要分清两层:

- **「全」= 覆盖该说的事**:当天每件主要产出都要出现(哪怕只是概述里一句 bullet + 一节两句话),不能因为想短就漏掉某件事或凭印象简化。完整性管的是**广度**。
- **「精」= 呈现要精简**:每件事**只展示需要展示的细节**,过程流水、内部技术细节、冗长枚举一律下沉或删除,深内容用 `<cite>` 指过去。精简管的是**每件事的深度与字数**。

一句话:**覆盖要全(广度不缩),呈现要精(每件事压到点子上)**。怕漏 → 在三方来源那步把事项收全;怕长 → 在这步把每件事砍到结论 + 引用。

## 一、收集当天的三方来源

**第 0 步 · 先确定「今天」是哪天(必做,先于一切)**:整理前先跑 `date +"%F %H:%M"` 拿真实日期与时刻,**绝不从 record 文件名 / 对话里提到的日期 / 产出文件去假设当天**。**凌晨算前一天**:若现在是凌晨(约 00:00–05:59),用户工作日还没翻篇,日报日期取**前一天**(`date -v-1d +%F`);凌晨产出的 record 通常落在次日日历日期的文件里,整理前一天日报时也扫一眼次日 record 文件的凌晨条目。日报标题与归档周子文件夹都用这个判定后的日期。若 record 日期与判定日期仍不一致(补写 / 记录滞后),**停下跟用户确认目标日期**再继续。

整理日报前,把当天工作的信息来源凑齐——不要只看其中一个:

1. **用户口述清单(主线)**:用户触发「整理日报」时通常会列出今天做了哪几件事、附参考文件 / 产出文件链接。这是最权威的当天工作清单,以它为骨架。
2. **产出文件(必读)**:对用户给的每个产出文件链接**实际回读**(见第二节),据此把每件事写准、写全——这是对抗"agent 记不住自己干过什么"的关键。
3. **md 记录(补充)**:取今天日期 `{YYYY-MM-DD}`(`date +%F`),读当天的本地 record 文件 `/Users/bytedance/Desktop/AI Workspace/Agentic Engineering/global-memory/memory/timeline-records/{YYYY-MM-DD}.md`(由全局 `memory-management` 的 time 子模块维护,文件内按 `## {HHMM}` 时间排序),以及用户指明的其他 agent 写的记录文件。有就整合进来,没有也不阻塞。
4. **前几天的日报(跨天去重基准)**:整理前先扫一眼最近几天已发的日报(`Daily Report/WeekN/`,拉 outline + 必要 section 局部读即可,不必全文),记下已经报过的事。**当日去重**:今天的条目若与前几天重复(同一产出/进展已报过),不再重复列;确属同一主线的延续,只一句点明「承接 X、今天新进展是 Y」,不复述旧内容。

> 三方都没有、用户也没口述 → 反问用户:今天做了哪些事、有哪些产出文件,便于整理。
>
> template 模式:本 skill 已封装 `templates/daily_report.xml`。整理时先复制该骨架,再用当天信息替换内容,保留其结构、callout 样式、表格与排版。

### 1.1 每个任务的检索归纳:并行子智能体,先读记录再外出

当天多个任务/条目的检索 + 归纳,**分给多个子智能体并行**做,不要串行一个个来——例如每个学习类任务各派一个子智能体,本职工作合一个。每个任务的处理顺序固定:

1. **先看当天 record 是否已有该任务的记录**:读当天 record 文件(路径见第一节第 3 点 = `…/memory/timeline-records/{date}.md`),**有该任务的记录就直接读用**——记录里已有要点 + 依据的 context 文件,不必再派子智能体。
2. **没有记录才派子智能体外出检索**:该任务在 record 里没有时,派一个子智能体去搜索相关的 **context 文件 + memory 文件**,理解该任务后归纳要点回传。
3. **任务没指定 context 文件时默认自己找**:任务没说 / 没指定依据的 context 文件,**默认自己找、自己补**,走 `references/retrieval-guide.md` 的标准检索路径(KB 索引 + 文档搜索 `drive +search`),**不要反问用户**。
4. **子智能体回传必带 context 文件**:每个子智能体理解 / 归纳任务时,回传内容里**必须讲清楚所依据的 context 文件(标题 + 链接)**,据此在正文就近引用。

> 检索的标准路径(怎么定位某任务的飞书文档)= `references/retrieval-guide.md`(单一权威)。本节只定「并行 + 先读记录后外出」的调度逻辑,具体检索步骤看那篇。

## 二、回读产出与 context 文件(质量保障)

对每件事,判断手上信息是否足以写清楚:
- **够清楚** → 直接成文。
- **不够清楚 / 需要准确引用 / 是当天学习重点** → 用 `lark-cli docs +fetch --api-version v2 --doc <url> --as user` 回读对应飞书文档全文。大文档优先按关键词/大纲定位需要的章节,不必整篇全读。顺着产出文件里的 link 可回读其依据的 context 文件,补前因/口径。
- **没有现成链接、要先定位文档** → 走 `references/retrieval-guide.md` 的标准检索路径(KB 索引「新增项」→ `drive +search` 交叉核对 → 逐篇 `docs +fetch`),不反问用户。
- **source 矛盾**:若片段 / 用户口述 / 原始文件之间口径冲突,结合自身知识取正确口径呈现,把矛盾点写出并标注来源,不漏写不瞎写。

## 三、日报归档位置与命名

- **位置(优先级:用户显式指定 > 默认)**:**用户给了明确的文件夹 / 路径 / folder token 时,优先落到那里,高于默认 `Daily Report/WeekN`**(显式指令以指令为准,不要为凑默认目录而移走)。未指定时才走默认:Drive `Daily Report` 文件夹 → 按周分子文件夹(`Week1` / `Week2` / …,当前阶段以用户最新指定为准)。文件夹不存在则创建(用 `drive +create-folder` 创建、拿 folder token)。
- **命名**:`📖 日报 {YYYY-MM-DD}`(面向人阅读,📖 前缀;标题不加括号)。
- **发布**:走官方 `lark-cli`(见 `feishu-task-management` 入口 + `cli.md`,用法见 `lark-doc-writer` §3)。XML body 用 `lark-cli docs +create --api-version v2 --content @file.xml` 创建,或 `docs +update --command block_*` 逐块落,落到目标周子文件夹。
- 若导入时无法稳定指定目录,可先建文档、再用 `drive +move` 把文档移动到目标周子文件夹。

## 四、日报结构

参考已封装的 `templates/daily_report.xml`(已验收的真实日报骨架)。

```
<title>📖 日报 {YYYY-MM-DD}</title>

[蓝色概述 callout]   — 一句话当天主线总览 + 逐条 bullet「做了什么」,每条对应正文一节

# 一、{任务一标题(名词短语,不加括号)}
  正文:动作 → 结论,结论先行;关键数据/方向用表格;事实句末 inline 引用 [[标题]](url)
  (子标题按需,如「跑实验」「分析调参」)

# 二、{任务二}
  ...

(每个任务一节,按片段时间或重要性排序)

---
[今日小结 callout] — 分维度收束当天价值(如实验侧/管理侧/基建侧),不只是复述;
                      **末尾加一句「下一步 / 明日动作」**(1 短句,见下「结构优化要点 5」)
```

### 结构优化要点

> 篇幅与裁剪的总原则见 §〇,本节是落到「结构」上的具体执行。

1. **概述简短**:概述先给一句「今天主线是什么」,再逐条 bullet 点明「做了什么」,让人不点开正文也能掌握全貌。**控制篇幅、不堆细节**——主线一句话、每个 bullet 一句话即可,得到的结论/细节留给正文。概述每个 bullet 对应正文一节,**一一对应**——不要把两件独立的事并进一条 bullet。
2. **不设 Context 段**:开头不放橙色 Context callout,引用统一在正文用 `<cite>` 或 inline `[[标题]](url)` 就近引用,正文也不单列「相关文档」节。
3. **结构化但不琐碎、不密集**:每节用「点题句(1--2 句自然话)+ 按需的要点 / 表格」组织——既不整篇碎成条目表,也不糊成密集长段(§〇「结构 ↔ 自然文字平衡」)。要点表达完整、读着自然,相关的点合并,不为拆而拆。多个并列对象/方向才上表格,先后顺序是重点的用列表;一句话能说清就别上结构。结论先行——表格/数据前先一句话点明判断。
4. **每节点到为止**:一节约 2--5 句的体量,讲清「做了什么 + 结论 + 关键逻辑」就停,深的内容用 `<cite>` 下沉,不在节内续写过程流水与背景铺垫(§〇 裁剪规则)。
5. **结尾给「下一步 / 明日动作」**:日报要让读者抓住「今天干了啥 / 什么问题 / 下一步」三件套——前两件正文已覆盖,**第三件靠小结末尾一句明日动作收口**(如「明日完成三篇对比并归档结论」)。即使当天动作都已完成 / 进行中,也补一句前瞻;**1 短句即可**,不展开成一节、不罗列待办清单。

### 分节铁律(按工作性质分节,强制)

> 日报是「今天做了什么」的工作记录,不是知识库。学习类工作与工具/系统构建类工作的写法不同:

- **一节 = 一件任务(= record 里的一个 `## 条目`),一一对应(最易错,先守这条)**:日报的「节」对应 record 的**任务条目**,不是它的子步骤。**别把一件任务的几个子步骤拆成多节**——「报告重组 / 修维恩图 / 产物归组托管」同属一件「分析收尾」任务,合成**一节**、子步骤作该节要点,不是立成 一、二、三 三节。**反过来,record 的每个 `## 条目` 都必须在日报出现**(对照逐条核对),别把整件任务(如「元系统 / harness 重构」)整块漏掉。下条「不同系统分开成节」指的是**不同条目之间**,不是把一个条目内部拆开。
- **学习类章节只列「学了什么」,不展开具体知识内容**:当天的学习重点(如吃透某套机制、读完某批文档),日报里**只列学到的主题/要点清单**(覆盖哪些概念、澄清了什么矛盾),具体的原理、公式、推导**留在学习文档本身**,日报用一条 `<cite>` 指向那篇学习文档即可。不要把学习文档的内容搬进日报(避免日报臃肿、与学习文档重复)。
- **不同 skill / 工具 / 系统的构建分开成节,但总节数 ≤5**:每个独立的大产出(一个 skill、一套系统)单独成节,职责清晰;**但当天事项多于 5 件时,把同性质的零散小事合并成一节**(如几处基建小修并为「基础设施补强」一节),或并入概述一句带过,不每件都立节(§〇 篇幅上限)。一节讲一件事,但「一件事」可以是合并后的一类小事。
- **每个构建类章节都要附「实例」引用**:建了某个 skill / 工具,就在该节用 `<cite>` 引用它**当天产出的实例文档**,让读者能点开看到真实成果,而不是只有抽象描述。
- **去冗余**:删掉自指式废话(如「这是今天唯一的学习内容」「下面来介绍」)、重复的总结句、跨节重复的背景交代。同一信息只在最合适的一处讲。

## 五、写作规则(从 lark-doc-writer / doc-trio 提炼,照此执行)

### 命名与前缀
- 面向人阅读 → `📖` 前缀;面向 AI → `🤖`。日报是 📖。标题用名词短语,**不加括号补充语**,括号内信息下沉正文。

### 格式
- **结论先行**:图/表/数据出现前先一句话点明核心判断,不让读者自己从数据里推。
- **结构化但不琐碎**:每节「点题句 + 要点 / 表格」,不堆密集长段;但要点表达完整、读着自然,相关的点合并、该用完整句子讲清逻辑就用完整句子,不为拆而拆。多并列对象用表格,有先后顺序用列表/流程。
- **控制文字量但保留必要解释**:每个 section 都要有新信息,删掉泛泛贴士、重复总结、常识。

### 风格(去 AI 化)
- 不写元说明导语:禁「本文目标」「接下来我们将」「读完你能」「我们来看一下」「咱们」。
- 不写 AI 腔排比铺垫、自我说明段。
- 语言像成熟工程师写的内部记录:自然、客观、不口语化;不加「(AI 撰写)」这类括号标注。

### Callout 节制
- 高亮 callout **默认就两个**:开头蓝色概述、结尾绿色小结(§〇 克制)。只有当天真有必须警示的事才破例加第三个,否则不加。
- 正文主体(任务叙述、表格)用普通 `<p>`/`<ul>`/表格,保留无高亮基础内容,不一屏堆多个高亮框。

### 开头标准结构
- 开头只放蓝色概述 callout(`background-color="light-blue" border-color="blue"`,emoji 📖 = `emoji_id:"book"`),保持简短:一句主线总览 + 逐条 bullet。
  - ⚠️ **callout 图标在 create 时设 `emoji_id`**:经 lark-cli 建 callout 易落默认 🎁(gift),事后改不掉;落概述用 `book`(📖)、小结用 `bulb`(💡)。落地配方见 `lark-doc-writer/references/mcp-recipes.md` 配方1。
- **不设橙色 Context callout**:不在开头集中列原始文件,引用一律在正文就近用 `<cite>` / inline `[[标题]](url)`。

### 引用
- 事实 / 数值 / 结论 / 原文 quote 句末 inline 引用 `[[标题]](url)`(放句号前);或用飞书 `<cite>` 资源块引文档。
- 引用来自片段「相关文件」区的链接;回读补充的也照引。
- 区分出处:产出文档 vs 依据的原始资料。

### 飞书排版硬规则(XML 模式)
- 颜色用语义化命名色(`light-blue`/`light-orange`/`light-green` 等),不用数字色。
- 表头 `<thead><th background-color="light-gray">`,列宽 `<colgroup><col width>`。
- 章节间用 `<hr/>` 分隔。
- 需要画图时(如链路图)按 `lark-doc-writer` §0.6 作图选型:要图就渲染成 PNG 嵌 Image(27) 块,纯文本兜底用 ASCII `<code language="text">`。⛔ `<whiteboard type="mermaid">` 经飞书 API 拍平,别用。日报一般以文字+表格为主,图按需。
- XML content 里裸 `<` `>` `&` 需转义为 `&lt;` `&gt;` `&amp;`(详见 `lark-doc-writer` §2)。

## 六、发布与回报

1. 把日报正文写成 XML body 文件(写到会话工作目录)。
2. 创建:用 `lark-cli docs +create --api-version v2 --content @file.xml` 把 XML body 建成飞书文档,标题 `📖 日报 {YYYY-MM-DD}`,落到目标周子文件夹。
3. 归档:若创建未稳定落到目标周文件夹,再用 `drive +move` 把文档移动到目标周子文件夹。
4. 回报用户:日报飞书链接、归档到哪个周文件夹、覆盖了哪几个任务。
5. (可选)整理完成后,当天片段可保留备查,不必删除。

> **改已发布日报(用户手动改过后)**:用户在飞书里手动改了某些段落(如修正数据、加 @人 review),再让你调整其他部分时,**绝不能整篇覆盖**(会清掉用户的改动、图片、评论、@人 mention)。正确做法:用 `lark-cli docs +fetch --detail with-ids` 拉块结构拿 block ID → 用 `docs +update --command block_insert_after / block_delete / str_replace` 在目标块前后插新块、删旧块、局部改概述等块。用户手动改过的块一律不碰。注意:对块做整体替换后块 ID 会重新生成,后续按 ID 操作要重新拉一遍(详见 `lark-doc-writer` §2)。

## 七、强制 checklist

- [ ] **先查日期(第 0 步)**:已跑 `date +"%F %H:%M"` 确认真实日期与时刻,**凌晨(约 00–06 点)算前一天**;标题/归档周用判定后的日期(不从 record 文件名/对话假设;凌晨 record 落在次日文件已一并扫;不符时已与用户确认)
- [ ] 三方来源都收齐:用户口述清单 + 实际回读产出文件 + 当天 md 片段,整合去重
- [ ] **多任务并行检索归纳**:每个任务先查 record 有无该记录(有则直读),没有才派子智能体;多任务分给多个子智能体**并行**;子智能体回传**必带依据的 context 文件(标题+链接)**;没指定 context 时按 `retrieval-guide.md` 自查不反问
- [ ] **覆盖全(广度)**:当天每件主要产出都出现(至少概述一句 + 一节),没凭印象漏写或简化掉某件事
- [ ] **节 ↔ record `## 条目` 一一对应**:对照 record 逐条打勾——每件任务一节(同一任务的子步骤不拆成多节)、无整件任务漏写(如「harness / 元系统重构」那种大块);子细节(口径表 / 具体数字 / 单图说明)下沉 `<cite>`,不在日报立节铺表
- [ ] **跨天去重**:已扫最近几天日报,今天条目与前几天不重复(同一主线的延续只点今天新进展,不复述旧的)
- [ ] 已复制 `templates/daily_report.xml` 骨架再替换内容(借排版,不照搬它 7 节的长度)
- [ ] 标题 `📖 日报 {YYYY-MM-DD}`,无括号,📖 前缀
- [ ] 归档位置:**用户显式指定的文件夹/路径优先**;未指定才落 Daily Report → 当前周子文件夹(不存在则创建)
- [ ] **篇幅 ≈ 1.5 页 / 一屏半**:一级节 ≤5(同性质小事已合并/并入概述)、每节约 2--5 句、**流动散文约 600--900 字**(口径:不含 callout/表格 cell/bullet 文字,别按全量字数误判超标),能很快读完
- [ ] **只留需展示的细节**:砍掉过程流水、内部技术细节、冗长枚举;深内容用 `<cite>` 下沉,不把学习/产出文档内容搬进日报
- [ ] **结构 ↔ 文字平衡**:不整篇条目表、不整段密文字;短自然句 + 适度结构,留白扫读友好
- [ ] 概述 callout 简短:一句主线总览 + 逐条 bullet「做了什么」,每条 bullet 与正文一节一一对应,不堆细节
- [ ] 不设开头 Context callout,引用一律正文就近 `<cite>` / inline
- [ ] 每节结构化但不琐碎:点题句(1--2 句自然话)+ 按需要点/表格,要点表达完整自然,结论先行
- [ ] 学习类章节只列「学了什么」清单 + `<cite>` 指向学习文档,不搬具体原理/公式进日报
- [ ] 不同 skill / 系统分开成节,每个构建类章节附「实例」`<cite>` 指向当天产出
- [ ] 去冗余:无自指废话、无重复总结、无跨节重复背景
- [ ] 讲清「做了什么 + 逻辑/原理」,讲到合适程度,不堆字也不浅到看不懂
- [ ] 事实/数据/结论句末 inline 引用或 `<cite>`,正文不单列「相关文档」节
- [ ] 去 AI 化:无元说明导语、无 AI 腔铺垫、标题无括号
- [ ] Callout 节制:仅概述/小结用高亮
- [ ] 今日小结分维度收束价值,不只复述;**末尾有一句「下一步 / 明日动作」**(让「今天干啥 / 什么问题 / 下一步」三件套齐全)
- [ ] XML 转义正确;回报飞书链接 + 归档位置
