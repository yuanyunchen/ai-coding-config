# Starmap 内容设计

图只解决"有什么、连到哪"。人打开面板是为了**看懂这个东西是什么**。
这份文档讲面板里放什么、按什么顺序放、什么不能放。

大部分规则来自同一条反馈：**做出来的面板全是统计数字，但人看完还是不知道
这张表是干什么的。**

## 第零原则：先定读者，再定内容（2026-07-30 加）

上面整份文档默认读者是「懂这套系统的同事」。**当产物要给团队外的人看时，标准还要再高一档**，
而这一档不是「写得更简单」，是**两条互相制衡的判据**：

> **正向**：把第一屏念给一个不写代码的同事听，他会不会中途打断问「这是什么意思」？
> **反向**：删到这个程度，一个真要用这张表的人，还拿不拿得到他要的东西？

只有正向那条，会一路删成一份谁都用不上的漂亮页面；只有反向那条，就是现状。
**两条同时成立才算过。**

由此推出的结构是两层，**下沉不是删除**：

| | 第一屏 | 附录（折叠，按主题分组） |
|---|---|---|
| 读者 | 非技术同事 | 要动手取数的人 |
| 语言 | 自然语言 | 允许 SQL、参数、字段全集 |
| 内容 | 是什么 · 从哪来 · 有什么 · 能不能用 | 怎么取数 · 用之前要知道的 · 完整参考 |

每一块从第一屏拿掉的内容，**必须在附录里完整可达**；第一屏里指向它的引用，
要么一起处理，要么做成可点指针。实测：面板第一屏从中位 15,000 字降到 1,400，**内容 0 处丢失**。

### 「第一屏」必须先定义边界

**这条不写死，两个方向都会出错。** 实测同一轮里：检查脚本只扫了正文，
页眉里的 `SELECT`、裸任务号、行话全部漏检；同一轮又有审查员因为只看正文，
误判「原始表名不见了」，而它一直在页眉里。

第一屏 = **页眉（标题 · 原始标识符 · 一句话定位）+ 关键事实 chips + 展开着的各节正文**。
折叠区里的不算。

### 第一屏禁用清单

出现即不合格：① SQL 片段与窗口函数；② 成串的内部参数（`seed_keep_n=100 · expand_n=200 · …`）；
③ 任务号 / 版本号当叙事主语（对象名可以出现，编号不该承担说明职责）；
④ 只有实现者关心的列（内部排名、签名、md5、存储键、审核状态枚举）；
⑤ 未经解释的英文大写标识（`READS_FROM`、`ADD`/`UPDATE`）；
⑥ 我们的行话（「口径」「血缘」「分层」「探测」）；⑦ 工程过程与自指（「本轮」「本节」「未探测」「留档」）。

### 第一屏必留清单

删掉即不合格：① 这是什么（带「一行 = 什么」）；② 从哪来（2–4 句自然语言）；
③ 谁产出它 / 谁在用它；④ 6–10 个人看得懂的字段；⑤ 一条真实记录；
⑥ 能不能用（有没有数据、新不新、会踩到的限制）；⑦ **原始标识符**——
非技术读者不用它，但它是这个对象的身份证，任何情况下不许删。

### 三条实测撞出来的细则

- **限定与警告不得排在被限定内容之后。** 一个块带着「这些数值是构造的、不要写进分析」
  这类警告时，警告要排在前面；两者都折叠时，警告那条折叠条也要在前面。
  **读者点开的一定是排在前面那条**——把警告放后面，等于确保它不被看见。
- **阈值跟着对象走，不跟着数字走。** 「核心字段 6–10 行」写死之后，
  只有 3 个业务列的表每一轮都被报成「筛过头」。正确写法是 `min(6, 全表业务列数) – 10`。
- **概述里提到的概念，对应字段必须出现在第一屏。** 实测：面板通篇在讲「一行是一块」，
  而定义这个「块」的字段被筛掉了——读者拿到了概念，拿不到实现它的东西。

### 对象的自我介绍，不许依赖它在链路里的位置

「它是整条选品链路的终点产物」「它是链路的内部层」——**放在第一节就是拿一个读者没有的
坐标系去定义这个对象**。读者可能根本不做这条链路的事，他只是要查商品信息。

更严重的一种是**用我们的建模决定解释它**：「它在本知识库里有一个节点，唯一理由是链路完整性」。
读者不关心我们的图怎么画。

同类还有**把链路上的约束写成对象的边界**。实测案例：一张商品主表的说明写着
「要商品属性、且日期在 `20260726` 及以后用本表」——那个日期是**下游链路换数据源的日子**，
不是这张表的可用范围，表有 30 天滚动数据每天都能用。这句话等于告诉所有查商品信息的人
「这张表只有三天可用」。**该日期不删，但要放回它成立的范围里说。**

上下游关系不要删，只是别放在第一节当定义——它在别的小节和图上都有。

## 第一原则：内容优先于统计

**字段覆盖率、空值率、基数这类指标不是面板的主角。** 它们是探测的副产品，
对"这张表能不能用"有价值，对"这张表是什么"没有价值。

一个具体的判据：**如果把面板里所有百分比都删掉，人还能看懂这个实体吗？**
不能，就说明你在用统计填充本该由内容占据的位置。

正确的主角是：一句话定位、核心字段的**业务含义**、一条真实记录、
标准取数写法、以及它和别的东西的关系。统计收进折叠区（`details.sm-more`），
需要的人点开就有，不需要的人不被它挡路。

## 面板结构

固定顺序，从"是什么"走到"怎么用"再走到"信不信"：

```
概述        3–4 段，人话，无跳跃                      ← 第一屏必须是它
关键事实    chips 一行放得下的硬指标（粒度、窗口、体量）
官方描述    如果有元数据系统，原样引用 + 外链
核心字段    字段名 + 业务含义 + 陷阱注解
嵌套结构    JSON / map / 事件序列的键清单（如果有）
数据实例    一条真实记录，只挑人看得懂的字段
标准取数    可直接跑的 SQL / 代码，带复制按钮
上下游      可点击跳转的关系条目
边界与缺口  没探测的、待确认的、不能下的结论
─────────  折叠线
统计明细    覆盖率、分布、枚举占比……
```

**每一节都要有可见的边界。** 只靠标题分节，长面板会糊成一片。做法是
分节标题（`.sm-sec`，左侧发光竖条 + 右侧渐隐横线）配合内容容器（`.sm-pane`，
弱边框 + 深底圆角）。这两个元素的作用不是装饰，是让人一眼看出"这块讲完了"。

## 概述怎么写

**是这个实体的概述，不是整个系统的概述。** 每个节点的面板里放系统级介绍，
等于每个面板都在说同一件事，而人真正想知道的那件事没人说。

3–4 段，每段 2–4 句。遵守 [Writing & Expression] 的"结论先行、逐层递进、
不跳跃、有具体数字"。

**不要依赖内部实现来解释业务。** 用"这张表记录用户与商品的行为关联"，
不要用"这是选品链路第二步、由任务 307331004 产出的中间表"。任务号、
链路阶段这些是**实现细节**，读者第一次打开面板时脑子里没有这套坐标系。
上下游关系有专门的一节，放那里。

**任务/流程类节点同样需要概述。** 只给一个任务号和"读 A 写 B"，
人不知道它到底干了什么。至少讲清楚：输入是什么、做了什么变换、
产出的语义是什么。

写完检查一遍：有没有"如图所示""综上所述"这类元评论，有没有形容词代替数字。

## 数据实例怎么选

**一条真实记录**比十个分布图更能让人理解一张表。但要选对字段。

**去掉 ID。** `product_id: 7292394480677389318` 对人没有任何意义 ——
它既不可读也不可记，只是占位。同理去掉 md5、hash、abase_key、
内部 status code、优先级数字、审核状态枚举。

**留下人能看懂的**：名称、地址、城市、价格、时间、类目、描述文本。
这些字段让人"哦，原来这张表长这样"。

排版用左窄右宽的键值网格（`.sm-kv`），左列可以带一行小注解释字段名：

```
name          Bali Ubud Rice Terrace Trekking Tour
              商品标题
location      Ubud, Bali, Indonesia
price_usd     42.00
```

含用户 ID 的表要做不可逆脱敏（截断或哈希），原始值不进文档。

## 嵌套结构必须展开

**JSON blob、map 字段、事件序列往往就是这张表的核心，而它在字段表里
只占一行。** 只写 `product_data: string(JSON)` 等于什么都没说。

必须展开成键清单：每个键的**路径、类型、含义、实测存在率**。

```
路径              类型      含义                    实测
info.title        string    商品标题                200/200
info.address      string    详细地址                198/200
ext.richText      string    富文本描述              200/200 有键，0 条有内容 ★
```

★ 这一行是真实教训：曾经把 `richText` 写成"富文本商品描述"，
听起来很合理。实测 200 条全部有这个键、**全部为空**。
**嵌套键的存在率必须实测，不能从键名推断语义。**

事件序列类字段同理 —— 要给出事件类型的词表和各自的含义，
而不是"这是一个事件数组"。

## 字段怎么筛

面板里的"核心字段"表不是字段全集。筛选顺序：

1. **ID 类放最前** —— 人第一眼要找的就是"用什么关联"
2. 业务主字段 —— 名称、金额、时间、类目
3. 分区/时间键 —— 决定怎么查
4. 有陷阱的字段 —— 单独加注解说明陷阱

**剔除**：常量列（全表同一个值）、审核状态、优先级、内部 md5、
存储键、明显的冗余重复列。这些进折叠区或干脆不进。

有一条容易搞反：**基数高不等于有信息量**。如果一个字段的
`top_value_share ≥ 0.99`，它实质是常量，不管基数多少都该降级。

字段的"含义"必须是业务语义，不是类型复述。
"`cost_units_1d`: decimal 类型的花费" 是废话；
"`cost_units_1d`: 当日花费，单位是平台内部计价单位、**不是货币金额**，
且有浮点尾数需要 ROUND" 才是有用的。

## 关系面板

边也要可点。关系面板讲三件事：

1. **这是什么关系** —— 产出 / 读取 / 观测到的数量关系
2. **证据强度** —— 血缘系统记录的？读代码确认的？还是只是实测数字？
   不同强度用不同颜色和虚实，并在面板里显式写出来。
3. **量化的事实** —— 如果有，给具体数字，并说明这个数字是怎么来的

关系里最有价值的往往是**反直觉的事实**。比如"这两张表同日 INNER JOIN
会得到近乎空的结果 —— 这是数据形态，不是 SQL 写错"。这种话能直接
省掉别人半天的排查。

## 事实纪律

星图看起来很权威 —— 深色、发光、精确的数字。正因如此，**里面每一句话
都必须可追溯**，否则它就是一台高效的谬误传播机。

四条硬规则：

1. **只写实测确证的。** 没查过的不写，推断的标注为推断。
   "听起来很合理"是最危险的信号 —— `richText` 就是这么错的。
2. **证据强度显式区分。** 血缘记录 / 代码确认 / 实测数字 / 待确认，
   在图上用颜色和虚实编码，在面板里用文字写明。
3. **排除项单列一节。** 哪些关系没画、为什么没画。
   一张只画确证关系的图，如果不说明排除了什么，读者会以为那些关系不存在。
4. **观测时间戳。** 每个数字都有保质期。顶栏读数条放全局观测日期，
   面板底部放本实体的探测时间和复核触发条件。

面板里出现"约""大概""可能"时，检查一下：是数据本身不确定，
还是你没查？前者要写明不确定的来源，后者去查。
