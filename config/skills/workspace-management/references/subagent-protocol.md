# 派发协议（v4）

第一节写给子智能体：派发的 task.md 首行会让你读这里。第二节写给主 agent。

## 一、给子智能体

你被派来完成一个任务，输入是一个 `task.md`，它所在的目录就是你的工作目录。

For dispatches under `.agent/`, follow the [v3 working-language rule](v3-legacy.md#在-v3-工作区里怎么做) for records and messages between agents.

1. **先读完再动手。** 读 task.md 全文（包括末尾的「追加」）和「必读」里的每个路径。你不继承主会话的上下文，也不会自动加载 skill；task.md 点名的规范和 skill 逐个读。
2. **只在授权范围内写。** 可写的只有你的工作目录和「可写范围」里列出的路径。工作目录里可以随意放草稿、中间结果、你自己的 plan.md 和 progress.md。不改 AGENTS.md、上层节点的任何文件、其他派发目录；没有授权不跑 git 写操作。**不制造审批弹窗、不碰别人的进程**：删除用固定路径（变量加 `${D:?}` 守卫），不用通配；只结束自己启动的进程（按 PID），不按名字 `pkill`。原因：posthog-dashboard 里通配删除反复弹窗要用户批准，宽匹配 `pkill` 三次误杀主会话的预览服务。
3. **新知识写进 memory 时标草稿。** 只有「可写范围」允许时，才在 `.agents/memory/<主题>/` 新建文件；frontmatter 写 `status: draft`、`source: <你的派发 ID>`、summary、type。改已有的 memory 文件也要得到授权。
4. **结果写进 result.md，自己写；核心进正文，复核材料进附件。** 路径是工作目录下的 `result.md`，结构参照模板 `templates/node/result.md`：
   - frontmatter `status` 只能是 `DONE`、`DONE_WITH_CONCERNS`、`NEEDS_CONTEXT`、`BLOCKED` 之一；
   - 正文写上层下一步要用的，控制在 6KB 内：「结论」先说结果；「需要上层处理」写全偏差、遗留、风险；「验证」每项一行（做了什么检查 → 通过/失败）；「产物」列关键文件；「写入 memory」列你写的文件；「附件」列表（文件、讲什么、什么时候看）。
   - 只有复核或排错才看的放工作目录里的附件：命令原始输出、逐条核对清单、完整文件列表、中间数据。上层要据此决定下一步的内容不许放附件；总量不大就不拆。
5. **该停就停。** 遇到以下情况，不要猜着往下做，写好 result.md 后返回：
   - 缺信息、要求互相矛盾 → `NEEDS_CONTEXT`，写清缺什么；
   - 需要写授权范围外的文件、环境或权限不满足 → `BLOCKED`，写清卡在哪、试过什么；
   - 成功标准做不到，或者任务应该拆成几块 → `BLOCKED`，给出拆分建议。
6. **聊天最后一行只回** `<STATUS> <result.md 的绝对路径>`，前面最多三行摘要。主 agent 以 result.md 为准；没有 result.md，你结束时会被拦下要求补写。
7. **被续接时**：上层发来"先读 task.md 末尾「追加」"的消息，说明有新要求。上一轮结果通常已被改名为 `result-rN.md`；如果你在收到消息前刚写出 result.md，它还没被改名，先自己把它改名为下一个 `result-rN.md` 再继续。读完追加按新要求做，结果写进新的 `result.md`；可写范围以追加里写的为准。

## 二、给主 agent

0. **模型分流**（总则见全局 AGENTS.md「subagent (dispatch)」，最低 sonnet，Explore/Plan 等内置类型同规；2026-11-16 用户裁决）：
   - 缺省继承主模型：派发时不传 model；用户没说要分流就不分流；
   - 用户说明要分流时按任务难度：影响功能质量的核心部分（判断、核心开发、质量把关、最终检查）仍继承；不影响功能质量的基础部分（批量替换、格式化、采集、跑命令）沿 fable → opus → sonnet 降一档；
   - 思考 effort 跟随模型：继承模型的派发同时继承 effort，降档的派发一律用 medium；每次派发都只给所需的最少材料，必读清单控制在个位数。
   - **该不该开子智能体**：要读文件、用工具、多步操作的才派发。输入给定、输出很小的单次判断（打分、两两比较、分类）用脚本批量调用模型，或交给一个子智能体批量做完。原因：posthog-dashboard 每次两两比较都开一个子智能体，读约 42KB、产出不到 1KB，评审类派发占四成，90 分钟的作业做了 7 小时。
1. **派发步骤。**
   - `ws dispatch <节点ID> <slug> --stdin`，从 stdin 传入四节：任务与背景、成功标准、必读、可写范围；同一节点多次派发共用的说明写进节点的 `brief.md`，会被自动列进必读；
   - 背景讲够（它不继承上下文），但规范类内容不重复粘贴：写进 `.agents/memory/`（type: convention）后在「必读」里引用路径。同一批派发共用的说明也这样处理；
   - 并行派发各自负责的文件不能重叠，在 plan.md「拆分」表里写明；
   - 用 `ws dispatch` 打印的那行 prompt 原样派发；hook 会拦下没有经过 `ws dispatch`、task.md 未填写、或已有结果的派发；
   - 外部执行（codex exec、claude -p）用 `ws dispatch --external`：命令行里让执行器先读 task.md，结果写回同目录 result.md。外部审查同样要留下记录，原因是 posthog-dashboard 两次 Codex 审查只留下节点根目录的两份文件，事后查不到当时让它审什么；
   - `ws dispatch` 发现新说明里有一段和以前的派发重复时会提示：那段就该进 memory 或 brief.md（见第 9 条）。
2. **回传处理。** 子智能体回报时 hook 会提示一行：它的状态、「需要上层处理」有几条、本波还有几路没回、节点已进行多久、还有几条要求没完成。照这个顺序处理：
   - **读 result.md，不读聊天回复。**
   - **「需要上层处理」逐条处理**：修（新派发、续派或自己改）、豁免（写理由）、报用户，三选一，每条用 `ws log <节点ID> --tag decision "Snn 第 k 条：修/豁免/报用户 …"` 记一行。这是核对意见唯一的落点；result.md 是子智能体的记录，你不改写。"交给后面的汇总或总决策参考"不算处理。原因：posthog-dashboard 里 22 份逐人分析报了自我回退、仅 AI 批准、片段压缩三类口径问题，主 agent 推给"总决策参考"，4.5 小时后外部审计重新指出，15 次派发返工，Top 5 换了 1 人。status 写 DONE 却列了待处理问题的，按 DONE_WITH_CONCERNS 处理；`ws check` 会列出还没有处理记录的。
   - **试跑先行**：同类派发要铺开（逐个候选人、逐个模块）前先跑一份，它报的问题处理完、口径写进 memory 或 brief.md 再铺开。
   - **按 status**：`DONE` 按成功标准验收，关键检查和关键数字自己重跑——子智能体会编造"运行输出"（2026-11-02 实测：没执行过命令却贴了一段输出）；`NEEDS_CONTEXT` 补信息后续派或新开；`BLOCKED` 解决阻塞或调整计划；`UNVERIFIED`（hook 代存）核对内容后改成正式状态，并记一笔。
   - **汇报节奏看产物是否已经摆在用户面前**：分析、采集、评审这类用户看不到中间态的派发，陆续回来时不逐个报，"本波已全部回齐"或遇到阻塞时说一次；产物是用户正在看的东西（线上页面、共享文档、仪表盘）时，每次发布都报一次，写明改了什么、是中间态还是完成态、还剩什么。原因：styles-study-taste 一天 47 次页面发布，用户两次说"不知道是中间结果还是结束了""还没看到任何更新"；有一次发布执行者没停下来汇报，主 agent 25 分钟后读中期结果才发现。
3. **独立验收。** 重要节点的结果交给另一个子智能体，按 goal.md 的验收标准检查；执行者不能自己判定完成。
4. **草稿转正。** 节点收尾前审阅 `source` 指向本节点的 draft memory：有用的改成 `status: stable` 或合并进已有文件，没用的删掉。
5. **长时间轮询的任务别依赖子智能体自己唤醒**（2026-07-04 实测，search-pixel-ad-side-increment）：后台 sleep 计时器到点不一定把它唤醒，任务会静默悬停。凡是"提交远端作业 → 等 → 收结果"的任务，二选一并写进 task.md：① 让子智能体在一个回合内持续工作，不交还控制，轮流检查各作业；② 主 agent 自己挂计时器检查产物是否落盘，停更就用 SendMessage 唤醒。
   - 往用户看得见的产物发布的执行者，每次发布后在 result.md 顶部写一行（时间、发了什么），并追加一行发布日志；主 agent 以发布日志为准判断"现在线上是什么"，不靠通知——执行者在等后台任务时不会回报。
6. **两个子智能体结论矛盾时，自己复现一次**（2026-07-31 实测，travel-catalog 召回链）。现场：A 报告某预检判据 `PASS EXIT=0`，B 和主 agent 各自实跑得到 `EXIT=1` 加一个 `KeyError`；原因是这个判据在不同解释器上给出相反答案，而它没声明自己跑在哪个解释器上。
   - 裁决依据是你自己的复现结果，不是任何一份报告，也不是"更近"或"更有把握"的那份；
   - 复现之后要问的是"两边什么不同"，而不是"谁对"。矛盾说明两边共同依赖的东西缺了一个前置断言，要修的是它：环境不满足时让它拒绝并说明，而不是给出一个答案；
   - 子智能体会自信地报告错误结果，纠正你时也可能是对的：两边都按证据采信，不按身份采信；
   - 在 task.md 的成功标准里要求"报告必须带可复现的命令和原始输出"，大多数矛盾会在回传时自己暴露。
7. **留档只追加。** 派发的 task.md、progress.md、派发目录都是日志，不改写；派发 task.md 唯一允许的写入是 `ws followup` 追加的「追加」段。节点 task.md 的「任务说明」例外：由上层随需求改写。
8. **续接还是新开。**
   - **续接原执行者**（SendMessage）：在原范围内修改它自己的产物、补一个小问题、它在等你回答。带新要求时先 `ws followup <派发ID> --stdin`：新要求、范围或可写范围的变化追加进它的 task.md，旧 result.md 自动改名为 `result-rN.md`，然后原样发出它打印的续接消息。只是催促或简单答疑不用 followup。
   - **新开派发**：产物不同、可写范围不同、需要另一种角色（开发 → 评审）、原执行者已经结束或上下文已经很长。
   - **续接有上限**：同一个派发续接到第 8 次（`ws followup` 会提示），或执行者的上下文明显变长时，不再续接：让它在派发目录写 handoff.md（当前状态、未完成项、踩过的坑、检查命令），余下的工作开新派发并在必读里引用。每节点 3 波的限制管的是新开派发，不是让一个执行者无限续接；波次用完就建子任务。原因：styles-study-taste 86 次派发共 260 次续接，其中两个执行者各被续接 55 和 54 次，上下文涨到 57 万和 96 万 token，一次简单的样式修改从读到追加到发布要十几分钟。
   - 原因：posthog-dashboard 里 12 条用户追加需求直接 SendMessage 给原执行者，原派发 task.md 一条都没记。结果是 task.md 写"占位原型"而交上来的是成品，有一份越界写进了未授权的目录，两份第一轮结果被第二轮覆盖丢失。
   - 续接前 hook 会提醒一次；消息里已经带了 followup 生成的 task.md 路径就不提醒。
9. **可复用的说明只写一次。**
   - 为什么：每次派发都重讲同一套口径，既占上下文又会不一致，下个会话还得从几十份结果里重新拼。posthog-dashboard 67 份派发结果一条都没进 memory：限流说明粘贴 5 次、评分标准 4 次；8 个子智能体各自发现同一个"越低越好的指标没翻转"bug；48 次评审派发都附带一份写给开发者、早已过时的 brief。
   - 写什么：可复用的模式和标准（评分口径、证据写法、比较规则）、做法（数据抓取与核对）、事实（代码结构、数据画像）、教训（踩过的坑）。
   - 什么时候写：试跑派发回来、口径定下来时；同一段说明要写进第二份派发时（`ws dispatch` 会提示）；节点收尾时。
   - 怎么用：跨节点的进 `.agents/memory/`，只服务本节点所有派发的进 `brief.md`；派发说明里只引用路径。数字不抄进派发说明，引用产出它的文件——抄进去的数字下一轮就过时。brief.md 只放本节点所有派发都适用的内容；开发和评审需要的说明不同时，说明它们该是两个子任务。
10. **几路派发往同一个对外产物发布时，先定发布规矩，写进节点 brief.md。**
   - 一个文件只有一个负责的派发；由几路的零件拼成的文件，拼装时取对方**当前线上**的那一份。
   - 不在线上文件上直接改：在自己的暂存目录里改、跑完检查，再替换；替换时保留上一版（`.prev`），并在发布日志里追加一行（时间、派发、改了什么）。
   - 锁只管替换：全部检查在拿锁之前跑完；持锁期间只做重新拼装、约 60 秒的冒烟检查、替换、写日志，然后放锁；完整检查放锁后再跑一遍，自己弄坏的就回滚。等锁超过 5 分钟的向上报告。
   - "回到上一个一致状态"指回到**本派发发布过并被验收的**上一版，不是更早的任何版本。
   - 预览服务器归主 agent：子智能体不重启、不换根目录、不占它的端口，自己要服务器就另开端口、用完按 PID 关掉。
   - 原因：styles-study-taste 的站点由 5 路派发同时改。持锁跑完整检查让一条紧急修改等了 10 分钟；两次有执行者直接改线上文件；一次回滚到了派发之前的旧版本；一次执行者用错误的根目录重启服务器，页面全部 404。这套规矩是当天一条条补出来的。
11. **紧急追加用固定写法。** 用户催的要求追加进 task.md 时写明四件事：排在哪些事之前；是否单独发布；这次用哪几项检查（其余的发布后补跑，查出问题就回滚）；多久内上线、上线后回哪一行。原因：用户 40 分钟里说了 5 次"快"，每次都是临时拼这四句；没写清顺序时执行者会先做完手头排在前面的事。
12. **向用户引用规则时带出处。** AGENTS.md「规则」节只记用户的裁决；主 agent 自己加的谨慎写进 brief.md 并标明是主 agent 定的、为什么。对用户说"按之前定的"之前先确认那一行的出处。原因：主 agent 把自己定的"每路最多 4 线程"说成用户的规则，用户纠正后才撤销，期间全量标注慢了几倍。
