# 派发协议（v4）

第一节写给子智能体：派发的 task.md 首行会让你读这里。第二节写给主 agent。

## 一、给子智能体

你被派来完成一个任务，输入是一个 `task.md`，它所在的目录就是你的工作目录。

1. **先读完再动手。** 读 task.md 全文（包括末尾的「追加」）和「必读」里的每个路径。你不继承主会话的上下文，也不会自动加载 skill；task.md 点名的规范和 skill 逐个读。
2. **只在授权范围内写。** 可写的只有你的工作目录和「可写范围」里列出的路径。工作目录里可以随意放草稿、中间结果、你自己的 plan.md 和 progress.md。不改 AGENTS.md、上层节点的任何文件、其他派发目录；没有授权不跑 git 写操作。
3. **新知识写进 memory 时标草稿。** 只有「可写范围」允许时，才在 `.agents/memory/<主题>/` 新建文件；frontmatter 写 `status: draft`、`source: <你的派发 ID>`、summary、type。改已有的 memory 文件也要得到授权。
4. **结果写进 result.md，自己写；核心进正文，复核材料进附件。** 路径是工作目录下的 `result.md`，结构参照模板 `templates/node/result.md`：
   - frontmatter `status` 只能是 `DONE`、`DONE_WITH_CONCERNS`、`NEEDS_CONTEXT`、`BLOCKED` 之一；
   - 正文写上层下一步要用的，控制在 6KB 内：「结论」先说结果；「需要上层处理」写全偏差、遗留、风险；「验证」每项一行（做了什么检查 → 通过/失败）；「产物」列关键文件；「写入 memory」列你写的文件；「附件」列表（文件、讲什么、什么时候看）。
   - 只有复核或排错才看的放工作目录里的附件：命令原始输出、逐条核对清单、完整文件列表、中间数据。上层要据此决定下一步的内容不许放附件；总量不大就不拆。
5. **该停就停。** 遇到以下情况，不要猜着往下做，写好 result.md 后返回：
   - 缺信息、要求互相矛盾 → `NEEDS_CONTEXT`，写清缺什么；
   - 需要写授权范围外的文件、环境或权限不满足 → `BLOCKED`，写清卡在哪、试过什么；
   - 成功标准做不到，或者任务应该拆成几块 → `BLOCKED`，给出拆分建议。
6. **聊天最后一行只回** `<STATUS> <result.md 的绝对路径>`，前面最多三行摘要。主 agent 以 result.md 为准；没有 result.md，你结束时会被拦下要求补写。

## 二、给主 agent

0. **模型分流**（总则见全局 AGENTS.md「subagent (dispatch)」，最低 sonnet，Explore/Plan 等内置类型同规）：
   - 要它做判断、核心开发、质量把关 → Opus（缺省）；
   - 要它给意见、做最终检查 → 继承主模型，只给结论所需的最少材料，必读清单控制在个位数；
   - 要它照单执行（批量替换、格式化、采集、跑命令）→ Sonnet。
1. **派发步骤。**
   - `ws dispatch <节点ID> <slug> --stdin`，从 stdin 传入四节：任务与背景、成功标准、必读、可写范围；同一节点多次派发共用的说明写进节点的 `brief.md`，会被自动列进必读；
   - 背景讲够（它不继承上下文），但规范类内容不重复粘贴：写进 `.agents/memory/`（type: convention）后在「必读」里引用路径。同一批派发共用的说明也这样处理；
   - 并行派发各自负责的文件不能重叠，在 plan.md「拆分」表里写明；
   - 用 `ws dispatch` 打印的那行 prompt 原样派发；hook 会拦下没有经过 `ws dispatch`、task.md 未填写、或已有结果的派发。
2. **回传处理。** 读 result.md，不读聊天回复。按 status 处理：
   - `DONE`：按成功标准验收，关键检查自己重跑——子智能体会编造"运行输出"（2026-11-02 实测：没执行过命令却贴了一段输出）；
   - `DONE_WITH_CONCERNS`：先处理「偏差与遗留」；
   - `NEEDS_CONTEXT`：补信息后新开一次派发（追加说明写进新 task.md）；
   - `BLOCKED`：解决阻塞或调整计划；
   - `UNVERIFIED`（hook 代存）：子智能体没按协议交结果，核对内容后改成正式状态，并在 progress 记一笔。

   用 `ws log <节点ID> "…"` 记下结论；result.md 是子智能体的记录，你不改写它的结论，核对意见追加在文末。
3. **独立验收。** 重要节点的结果交给另一个子智能体，按 goal.md 的验收标准检查；执行者不能自己判定完成。
4. **草稿转正。** 节点收尾前审阅 `source` 指向本节点的 draft memory：有用的改成 `status: stable` 或合并进已有文件，没用的删掉。
5. **长时间轮询的任务别依赖子智能体自己唤醒**（2026-07-04 实测，search-pixel-ad-side-increment）：后台 sleep 计时器到点不一定把它唤醒，任务会静默悬停。凡是"提交远端作业 → 等 → 收结果"的任务，二选一并写进 task.md：① 让子智能体在一个回合内持续工作，不交还控制，轮流检查各作业；② 主 agent 自己挂计时器检查产物是否落盘，停更就用 SendMessage 唤醒。
6. **两个子智能体结论矛盾时，自己复现一次**（2026-07-31 实测，travel-catalog 召回链）。现场：A 报告某预检判据 `PASS EXIT=0`，B 和主 agent 各自实跑得到 `EXIT=1` 加一个 `KeyError`；原因是这个判据在不同解释器上给出相反答案，而它没声明自己跑在哪个解释器上。
   - 裁决依据是你自己的复现结果，不是任何一份报告，也不是"更近"或"更有把握"的那份；
   - 复现之后要问的是"两边什么不同"，而不是"谁对"。矛盾说明两边共同依赖的东西缺了一个前置断言，要修的是它：环境不满足时让它拒绝并说明，而不是给出一个答案；
   - 子智能体会自信地报告错误结果，纠正你时也可能是对的：两边都按证据采信，不按身份采信；
   - 在 task.md 的成功标准里要求"报告必须带可复现的命令和原始输出"，大多数矛盾会在回传时自己暴露。
7. **留档只追加。** task.md、progress.md、派发目录都是日志；重试或补充要求用新派发，不改旧的 task.md 正文。
